# 历史发布说明：截至 0.3.80

以下为原 README 发布说明，开关与行为仅代表当时版本。当前使用说明见 [README](../../README.md)，历史条目不能替代当前合同。

## 0.3.80 回退未达标语义实验

撤回 0.3.76–0.3.79 的有限域、SAT 与独立来源复核，工作包功能恢复 0.3.75，V2 及其确定性范围修复保持开启。保留数据库迁移兼容性、历史评测证据和页面测试清理；含实验合同的数据不会被静默降级。详见 [回退范围和数据边界](../package-behavior-rollback.md)。

## 0.3.75 工作包 V2 默认启用与冻结范围加固

新建工作包设计默认使用 V2，自动包含冻结证据、来源关系、缺口分类和按复杂度触发的一次语义整理；无需再单独开启证据开关。`LOOPPER_PACKAGE_DESIGN_V2_ENABLED=false` 可将新会话回退到 V1，既有会话继续冻结版本。

服务端在接受 V2 前证明 Stage 和 GIT_DIFF 的允许路径不超出冻结范围，拒绝候选新增路径扩大授权，并保留删除保护。集合删除与“将该文件移动”等原文请求在候选之前阻断，不能包装成 ANY 分支。固定提示补充首次状态转换、重复请求与优先级分支的完整表达规则。自然语言覆盖仍需独立复核，来源图不是语义完备证明。验收结果和运行边界见 [V2 加固与启用](../package-design-v2-enablement.md)。

以下章节记录历史交付时的开关状态；当前默认以上述 0.3.80 为准。

## 0.3.74 Codex Luna 配对评测与语义验收

补齐订阅 Luna 同会话整理/续跑、逐候选独立清单复核、可复现汇总脚本与 V2 恢复/停止隔离测试。生产核心仍使用已冻结的 V2 合同与固定 Prompt；默认开关保持关闭。详见 [三批优化与评测证据](../package-design-luna-optimization.md)。GEPA 因无法在每次真实模型请求前执行总预算，停在适配器验证阶段，未启动优化请求。

## 0.3.72 工作包 V2 与一次语义整理

- 新建且匹配 V2 会话的运行可通过 `LOOPPER_PACKAGE_DESIGN_V2_ENABLED=true` 使用有来源的语义合同；默认关闭，旧会话/旧候选和 Role Pack 不升级。
- 支持 `all / any / unless` 关系图（32 节点、4 层），全部适用分支继续验收。一次只读语义整理按修订持久化，简单任务与已有问题回合不增加整理请求。
- 来源未知、待建测试、真实业务选择和已证实冲突分开处理。明确的业务选择可通过本地反馈 `REQ-L001=最终行为` 补充，原文保留；模型自述不能成为用户决定。
- V2 提交工具与旧工具隔离，阶段合同和权限仍由服务端生成。源码/测试交付不代表 Luna 配对门槛或活动 OpenCode 链路已达标；详见[三批优化说明](../package-design-luna-optimization.md)。

## 0.3.70 工作包证据与 Luna 评测基础

- 新增缺口证据分类和 V72 不可变证据快照；新策略默认关闭，只为新运行冻结，历史候选保持原合同。模型缺口码不再单独构成业务缺失的证明。
- 新增 ChatGPT 订阅 Luna 的隔离 Codex MCP 评测桥接器和 36 个固定案例，直接调用生产 Prompt、Schema、编译器及真实修复回执。编译通过仍须独立语义复核。
- 详细范围、命令、质量门和 GEPA 请求预算限制见[三批优化说明](../package-design-luna-optimization.md)。本批尚不启用 V2 或宣称生产首投率达标。

## 0.3.67 七角色 MCP 同步优化

- 拆解、工作包、验收闭集、滚动计划、Reviewer、公约和 Judge 的工具约束与生产校验同步：明确引用索引、集合大小和 UTF-8 字节边界，中文原因不会被错误的字符上限替代。
- 修正反馈推广到全部内部 MCP 角色。形状问题优先呈现，保留角色安全及冻结输入检查；稳定问题标识区分已解决、仍存在和新增问题。Judge 修复格式时必须保留证据支持的判定。
- V71 允许其余六个角色分别配置 2–16 次总提交上限，默认 `0` 继续不限次数；新运行冻结配置，旧运行和 Legacy 预算保持。具体环境变量、三批次内容与隔离评测证据见 [七角色优化说明](../mcp-role-optimization.md)。

## 0.3.66 MCP 设计候选优化

- 结构化候选按 key 直接编译，重复标题不再造成引用歧义；人读 Markdown 和来源证据仍由服务端生成。场景、事实和阶段上限提前公布并定位到实际数组。
- 冻结需求/范围冲突在模型调用前检查。候选错误先区分权威边界、结构和语义，修正反馈增加已解决、仍存在和新出现的问题标识。
- 可选 `LOOPPER_PACKAGE_DESIGN_CORRECTION_LIMIT=4` 将新工作包运行限制为首投加最多三次修正；默认 `0` 保持无限提交，已有运行沿用冻结策略。重复候选或预算耗尽进入待输入，幂等重放不消耗次数；不会降低路径、测试或权限校验。
- 三批次范围、真实模型对照的方法和证据边界见 [优化与评测说明](../mcp-design-optimization.md)。本次小样本不能代表生产通过率。

## 0.3.64 MCP 中文长诊断修复

- 候选正文继续使用独立的 128 KiB UTF-8 总上限；单条诊断字段的 1 KiB 上限只约束返回给模型的错误信息，不限制合法中文设计稿。所有诊断展示字段现在按 UTF-8 字节安全截断，不再按 Java 字符数截断后被持久化边界拒绝。
- 根级 `/candidate` 问题返回对象类型、UTF-8 大小和顶层字段摘要，不再把整个长候选复制到 `actual`。中文、emoji 或中英文混排的可修正问题继续得到 `OPEN / REJECTED / FIX_AND_RESUBMIT`，不会退化为 `INTERNAL_CANDIDATE_SUBMISSION_FAILED`。
- 任一诊断字段或允许值因协议字节边界被截断时，响应明确设置 `diagnosticsComplete=false / truncated=true`；模型仍可在同一候选 Session 提交完整替换对象，服务器不会把不完整列表冒充完整诊断。

## 0.3.63 MCP 精确语义诊断与人工输入边界

- `CANDIDATE_DIAGNOSTIC_V2` 不再为语义失败生成 `value satisfying ... / value at ... does not satisfy ... / Replace candidate` 这类占位信息。每条问题绑定模型调用参数 `candidate`、精确 JSON Pointer、该位置的有界实际值、预期约束、具体原因和可执行修复动作；工作包验收问题还绑定 `SC-* / REV-*`、阶段名、全部重复位置以及候选中的相关原句。
- 工作包的验收能力、事实归属、阶段引用、依赖与覆盖现在一次确定性遍历收集全部独立问题。任务拆解、滚动分包、Judge 和项目公约的闭集错误也定位到具体数组元素；`diagnosticsComplete=true` 只表示该轮有界检查确实完整，超过上限时明确返回截断状态。
- `AMBIGUOUS_ACCEPTANCE_INTENT`、`VERIFICATION_CAPABILITY_UNAVAILABLE` 和 `REQUIRED_MUTATION_PATH_UNASSIGNED` 属于候选可自行修正的问题。模型即使把它们包装成 `NEEDS_INPUT`，运行也保持 `OPEN / FIX_AND_RESUBMIT`，不能再借此误停到人工处理；只有缺少用户拥有的成功语义、范围选择、大型任务确认或冻结安全边界冲突才允许 `STOP_AND_WAIT_FOR_INPUT`。
- 七个角色仍共享一个私有 MCP Server 和统一持久化内核，但每个新 Session 只看到本角色唯一的强类型提交 Tool；完整对象提交保留原子替换语义，不拆成会留下半成品的逐字段 setter。

## 0.3.62 历史任务脏文件误报与取消修复

- `WAITING_INPUT` 的当前原因改由最新 Task 状态转换权威给出；新转换写入 `reason_code`，旧内网数据只在当前等待轮次内从转换元数据或错误兼容推导，不再扫描整段错误历史。
- `SOURCE_BRANCH_WORKSPACE_DIRTY` 仅在任务分支和执行目录都尚未准备时有效。已经有分支或阶段执行记录的历史任务不会再弹出空的“发现未提交文件”窗口。
- 已经打开的旧弹窗仍可使用“取消任务并保留文件”：服务端会转入统一 `STOPPING → CANCELLED` 协议，保留现有文件、任务分支、执行目录与审计证据，不再被过期的脏文件动作守卫拒绝。

## 0.3.61 内网 Router 步数兼容修复

- Router 仍只接受一次任务分类业务结果，但受管 `loopper-router` Agent 改用 2 步传输上限。OpenCode 会把配置的最后一步改造成禁用工具的文本收束步骤，因此 1 步配置会在第一次调用就注入 `CRITICAL - MAXIMUM STEPS REACHED`；2 步只为首个业务回合避开该控制提示，不增加第二次分类或工具权限。
- `OPENCODE_STEP_LIMIT_REACHED` 现在从 HTTP 结果识别一直保留到 Router run，不再被泛化成 `ROUTER_OUTPUT_INVALID`。任务设置活动投影同时隐藏这段 OpenCode 控制提示，仅展示中性的整理状态。
- 新配置只会由新版受管 OpenCode 进程在启动时加载，不会热改已有进程。升级 JAR 后需在运行环境页显式重启受管 OpenCode，或重启 Loopper；外部 `auto/http` OpenCode 的 Agent 配置仍由操作者管理。

## 0.3.60 角色专属 MCP、精确批量诊断与并发冻结幂等

- 私有候选 MCP 仍是一个 loopback/Bearer Server，但新运行按角色只开放一个强类型 Tool：任务拆解、验收选择、工作包设计、滚动计划、Reviewer、项目公约和 Judge 分别使用 `submit_decomposition_plan`、`submit_acceptance_choice`、`submit_package_design`、`submit_rolling_package_plan`、`submit_reviewer_report`、`submit_project_convention` 和 `submit_judge_decision`。每个 Tool 直接公布该角色的闭集对象 Schema，模型不再面对一个含义随 run 改变的通用大参数。
- 拒绝响应升级为 `CANDIDATE_DIAGNOSTIC_V2`：一次遍历聚合独立问题，并对每项给出 `parameter / pointer / category / expected / actual / detail / allowedValues / repairHint`。`diagnosticsComplete / problemCount / returnedProblemCount / truncated / action / submissionRevision` 明确告诉模型问题列表是否完整、下一步是什么以及应使用哪个修订，避免靠通用报错猜字段。
- 每次仍提交一个完整替换对象，不拆成会产生半成品状态的逐字段 setter；七个角色 Tool 只负责缩小认知面，随后统一进入 `MachineCandidateSubmission`、角色确定性 compiler/policy 和 DB-only accepted writer。路径、命令、测试、权限、稳定 ID、生命周期及安全结论仍由服务端拥有。
- 冻结旧 launch 继续识别私有 `submit_candidate`，进程内 Legacy 继续接受旧角色格式；新 launch 不授予旧工具或其他角色工具。历史兼容只用于恢复，不会成为新模型的宽松入口。
- Convention 请求线程与 Monitor 同时冻结来源时，仅当 candidate run 以及来源、owner 版本、合同、内容哈希、栈画像和证据全量一致才把重复写视为幂等；不同 run 或任一字段漂移仍失败关闭，不会把 SQLite 唯一约束伪装成模型错误。

## 0.3.57 故事统计 start 失败降级

- 新统计会话仍先调用 `aicoding start`；只有 start 返回明确失败时，才在同一远端 Session、同一系统/故事编号下自动补发一次 `aicoding continue`。
- start 与 continue 分别持久化消息 ID、结果和 `retry_of` 调用链。continue 成功时不再发送失败通知；continue 也失败时只通知一次，且不会继续递归重试。
- 结果未知、进程中断或用户取消不会自动补发，避免重复统计；人工重试会保留失败调用原本的 start／continue／complete 操作。

## 0.3.56 MCP 可修正问题续投

- 工作包 `READY` 候选中的内容遗漏、覆盖不全、验收归属与验证能力歧义会返回可执行的 `code / JSON Pointer / detail / allowedValues`，保持同一 run 与 Session 为 `OPEN`，不再误进人工恢复。
- 验收选择的安全合同形状错误、滚动计划的根结构/载荷错误，以及 Reviewer/项目公约的普通额外字段均允许同一 MCP Session 修正；路径、权限、安全、身份、执行权威和真实人工缺口仍失败关闭。
- 所有候选角色提示都要求消费完整问题信息和返回的 `submissionRevision`；页面将真实累计数显示为“候选提交”，不再把全部提交误称为“候选修正”。

## 0.3.55 全角色提示适配

- 开发与恢复使用当前阶段完整验收合同、Judge 准则和验证服务启动配置；历史设计和重试摘要只作背景。
- 需求讨论与任务规划接入已确认 Role Pack；滚动包使用最新检查点事实，历史聚合设计保持执行前合同语义。
- Router 明确全部制品枚举；MCP 提示补齐嵌套字段、人工评审及缺口模板，沿用 0.3.53 的无提交次数上限。
- 规范工程师按历史合同代际输出；评审、项目公约、提交建议、合并和统计角色分别明确证据与输出边界。

## 0.3.53 取消 MCP 候选提交次数上限

- 设计师、拆解器、验收选择、滚动规划、Reviewer、项目公约和双 Judge 均不再受原 2 / 3 / 5 次 MCP 提交上限限制；可根据拒绝反馈继续修正。
- 成功提交后结束当前候选；实际提交次数继续记录，重复请求保留幂等性。权限、来源、版本、验收和非可修复错误仍正常校验。
- 升级保留历史候选、响应与数据库约束；活动候选使用新规则，已结束候选不会自动重开。MCP 提交次数与角色步数、超时及模型调用预算分别管理；非 MCP 的 Legacy 格式修复预算保留。

## 0.3.51 按角色取消固定步数上限

- 设计师（需求、工作包及 MCP 候选）、执行者、Reviewer 和 Requirement/Risk Judge（含恢复收尾）均不受 Loopper 固定 24 步限制。
- Decomposer、Compiler（含绑定、修复、验收选择）、滚动规划、项目公约和非 Judge 通用收尾保留 24 步；Router 保留单次业务分类并使用 2 步 OpenCode 传输上限，独立工作量统计命令保留 2 步。
- 重复工具检测、角色超时、Task 预算、权限与验收继续生效；该版本保留的 MCP 候选次数上限已在 0.3.53 取消。OpenCode 步数上限控制提示会明确报告失败，不再保存为设计稿或送入验收编译。
- 新配置随新版受管 OpenCode 启动生效；已有进程不会热更新，已有错误设计稿不会自动改写。外部 OpenCode 的 Agent 配置仍由使用者管理。更新运行环境后重新发起受影响的设计或评审。

## 0.3.49 设计师会话复用

- 单包需求讨论、设计、修改和返修共用一个 Session；多包全局讨论独立，每包各用一个 Session。
- 等待回答、编译和待确认不结束统计；真正交接后才 complete，单包正常设计只有一组自动 start/complete。
- V68 持久化会话与回合身份，恢复不盲目重发；交接后重开新轮次，升级前设计继续旧策略。详见 [故事统计说明](../story-binding.md)。

## 0.3.44 统计交接与人工重试

- 旧会话的 complete 返回或手动取消后才交接下一次 start；自动清理不再中断正在提交的统计。
- 统计弹窗可手动重新发起失败的 start／complete，V67 保留每次调用、输出和错误记录；业务或提问仍占用原 Session 时暂不可重试，避免中断任务。
- 该版本不做自动重试且不增加统计超时；0.3.57 起仅为明确失败的 start 增加一次 continue 降级，失败仍继续业务。详见 [故事统计说明](../story-binding.md)。

### 0.3.42 故事绑定与工作量统计

- 开始设计时可选开启故事绑定，先检测项目所连接 OpenCode 的 `aicoding` 命令，再填写系统编号与故事编号；普通与附件提交一致。
- 仅需求设计师、工作包设计师和执行者统计；每个新 Session 都使用 `start`，业务结束后尝试 `complete`，复用同一 Session 不重复开启；全局弹窗显示统计进度、真实模型输出和取消按钮，持续等待不再自动超时；取消或统计失败后任务继续。
- 统计回合与设计师提问分开处理：统计工具可用，统计结束后继续正常提问；Router、规划和各评审角色不统计。
- 配置继承到任务、重试与 Recovery；V65 持久化调用身份和结果，重启不盲目重发。统计消息与业务消息分流，受管 OpenCode 使用独立统计 Agent 和原生消息/工具保护插件。
- 使用真实 OpenCode、开发用模拟插件和 localhost 接收端验收；内网插件的回执及并行语义仍需现场验证。详见 [故事绑定说明](../story-binding.md)。

### 0.3.33 附件全角色与评审修复

- 修复默认 MCP 双 Judge 漏传附件：需求/风险评审均读取任务冻结的整体需求与全部工作包附件，Recovery 继承后同样适用。
- 消除 Judge 提示中“多行 Markdown”与“单行理由”的冲突；Reviewer 明确 `limitations` 为字符串数组，并返回准确字段修复提示。权限、证据和危险控制字符校验不放宽。
- 不重放历史失败会话，不自动重启服务；请确认运行版本后重新验证。

### 0.3.32 MCP 附件资源修复

- 附件改为私有 MCP Resource：发给 OpenCode 的是受控资源 URI 和来源描述，不再发送受管文件路径或内联文件字节。OpenCode 通过 `resources/read` 读取完整快照，Loopper 再回读它保存的输入并校验内容哈希；读取失败或内容缺失均阻断，不静默忽略附件。
- DOCX/XLSX/PPTX 原件仍保存、校验及冻结，模型只读取版本化确定性文本，不包含嵌入图片或页面布局。文本/JSON/CSV/XML 及提取文本限 128 KiB，规避 `.bin` 被误判及 Read 截断。图片/PDF 通过 MCP blob 保留可视内容，单个二进制资源最多 10 MiB，且仍需模型支持其格式。
- 使用受管 OpenCode 的 loopback/Bearer 私有 MCP，不提供公开下载链接、不开放附件全局枚举、不扩大目录或候选工具权限；资源是按远端 Session 和运行代际签发的不可猜测读取凭据，15 分钟有效，确认停止会话即撤销。非受管连接明确拒绝附件，无附件流程不受影响。
- 模型不支持附件格式时显示明确原因，不再只提示“设计失败”。升级不会修改历史或自动重放失败会话；确认“运行环境”的 Loopper 版本后重新开始设计。真实验收需验证模型引用仅存在于附件的内容，HTTP 接收成功不等于读到附件。

### 0.3.30 附件消息 ID 修复

- 修复添加附件后设计请求被 OpenCode 拒绝：自动生成的附件消息 ID 现在满足其协议前缀要求，TXT、DOCX 等共用同一修复。文件完整性、作用域及“不可信参考”边界不变。
- 设计恢复提示和系统消息不再被外层错误包装遮蔽，会显示“设计请求未能发送给 OpenCode”及版本兼容性、连接检查方向。历史附件与错误记录保留；升级不会自动重放已失败的设计，请使用新版本重新发起设计。

### 0.3.28 任务体验更新

- 最终 AI 双评审只作参考。确定性阶段验收已通过、评审和写入者都已停止时，在任务双评审区点击“人工认定通过”，确认后即可沿现有流程提交、推送和创建合并请求。原始 AI 结论保持不变，人工认定单独留痕；不能跳过实际执行失败或尚未停止的会话。
- 任务规范化提示按任务和提示内容去重，重新进入页面不再累计；冻结设计对话只展示用户、设计师和结构化需求讨论，完整角色审计仍在持久化历史中。
- “系统 → 工具”按全局运行环境或项目展示当前 OpenCode MCP 连接状态；展开服务读取工具及描述。工具清单不执行工具，支持本地 stdio、远程 Streamable HTTP/SSE；OAuth 令牌无法由配置取得时会显示读取不可用，需在 OpenCode 检查授权。只对已连接、已有配置的服务进行读取，不启用停用的 MCP。
- “用量与质量”支持项目、任务状态、质量、归档和标题筛选；列表、总 Token 和分币种成本使用同一筛选范围，分页不改变汇总口径。人工通过与 AI 通过分别显示。
- 取消仍占用登记目录的 Git 任务时，先确认写入者停止，将未提交和未跟踪修改保存到私有 checkpoint/stash，再切回本地默认主分支（origin/HEAD 对应分支，其次 main/master）。分支、文件快照及证据保留；不能安全保存或切换时保留租约并显示阻塞。待开始、排队任务和其他任务的租约不受影响，Direct 模式不切换分支。
