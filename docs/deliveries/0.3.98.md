# 0.3.98：develop 起始分支的取消任务租约回收

## 问题与修改

旧任务已取消、写租约仍保留时，登记目录可能已回到任务记录的起始分支 `develop`。原取消流程选择仓库默认分支（origin/HEAD，然后 main/master），却只允许从任务分支执行切换；当起始分支与默认分支不同，就会返回 `TASK_SOURCE_BRANCH_RESTORE_MISMATCH`，新任务一直排队。“重新检查并释放”重复同一判定，无法解除。

修复保留取消后恢复默认分支的合同，增加有证据的中间恢复状态：当前分支确实等于该任务持久化的 sourceBranch，且写入已停止、目录身份一致、工作区干净时，可以继续恢复默认分支，再释放／转移 FIFO 租约。正常完成仍恢复任务起始分支。无关分支、detached HEAD、未保存文件和未确认停止的 writer 继续阻断。缺失起始分支证据的历史任务不能通过当前分支名称猜测已恢复；仍仅接受任务分支或已经恢复的默认分支。

分支恢复逻辑从接近规模上限的 GitWorktreeManager 提取到专门的 GitSourceBranchRestorer；错误详情附带释放目标和记录的起始分支，保留原错误码。恢复操作仍在数据库事务外，没有新增迁移、强制切换、reset 或删除文件。

此前 0.3.97 的 story 延迟矩阵使用 main 同时作为起始与默认分支，未覆盖这个分支组合。本次补充 develop→main、develop→master、develop→origin/HEAD 指向的 release，以及普通任务和重做任务的租约回收测试。

## 重复验收

`scripts/qualify-branch-release.py` 在独立目录和端口启动指定 JAR，使用 fake OpenCode、真实 Git 与 HTTP 接口，不调用 Provider。普通与重做两项场景均先验证无关分支和未保存文件被阻断，再将起始分支上的测试文件提交保存，调用“重新检查并释放”同一接口，核验下一任务进入 RUNNING、重复调用幂等以及 develop 的提交和文件内容未改变。最后停止本次 JVM，保留 results.json 和 loopper.log。

```bash
JAVA_EXECUTABLE=/绝对路径/jdk21/bin/java python3 scripts/qualify-branch-release.py target/opencode-loopper-0.3.98.jar
# 对旧版本复现已知阻断，增加 --expect-blocked
```
