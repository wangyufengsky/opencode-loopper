# 0.3.88：恢复文档设计的最终确认入口

## 问题与根因

用户在 0.3.87 重新生成 CupXml2Java 文档设计后，页面已经显示 DRAFT_READY、FINAL_REVIEW 和有效验收计划，但两个“确认设计并创建任务”按钮均禁用。现场只读 API 证据显示：任务画像 FROZEN / DOCUMENT_AUTHORING / OPEN_CODE_IMPLEMENTATION，阶段 DOCUMENT_AUTHORING、artifactPlanId=null，而 finalConfirmationEligible=false。

0.3.87 将文档改为 Start 后由 OpenCode 实际撰写，却遗漏了 Designer 最终确认资格判断：该判断仍要求所有直接/分包制品有一个 FROZEN artifact_plan。旧执行回归直接调用 drafts.confirm，未检查 Designer DTO 的 finalConfirmationEligible，因此没有发现页面入口断点。

## 修改与兼容

- 把直接制品的确认策略集中到 DirectArtifactConfirmationPolicy。文档撰写依据冻结文档画像、OpenCode 实施策略、对应交付路径的文档检查及已规划正文评审获得确认资格，不再要求旧的物化计划。
- 简单文档和多章节文档共用该判断。已持久化并停留 FINAL_REVIEW 的新式文档设计在读取时即可恢复确认资格，无需数据迁移、重填需求或重写冻结规格。
- 历史文档物化、表格转换继续要求原 FROZEN 计划；本地维护和完整工作包审批条件保持原逻辑。未冻结或策略不匹配的文档画像、只有格式检查的文档不能通过新分支。
- 前端继续消费服务端确认资格，不硬编码放开按钮。确认只创建 PENDING_START；正式 Start 后才有撰写 Session。
- 同步设计合同，降低 DesignerSessionService 的结构债务行数上限。
