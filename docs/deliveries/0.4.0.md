## 共享内存数据库并发夹具修正

首轮 macOS CI 的 `MachineCandidateSubmissionIntegrationTest.cleanupStopClaimFencesConcurrentAbortAndOnlyExpiresIntoOneCrashTakeover` 触发 `SQLITE_LOCKED_SHAREDCACHE`。原因是该类沿用共享内存 SQLite，多连接读写存在表级共享缓存锁，与生产文件数据库 WAL 的并发行为不同；同轮 Linux 完整门禁通过。原始日志 `/tmp/loopper-040-macos-first.log` 保留。

该测试类改用独立临时文件数据库、WAL、busy timeout 和 IMMEDIATE 事务模式，沿用其他并发集成测试的方式；保持原夹具外键策略。停止争抢用例显式核对 WAL，仍验证两名竞争者恰好一名取得执行权、TTL 内不可接管、过期仅一次接管、旧 fence 不能提交停止结果。未修改生产数据库参数、生产停止逻辑或重试次数。

`./scripts/dev-check.sh backend MachineCandidateSubmissionIntegrationTest` 48 项通过，失败 0、错误 0、跳过 0；日志 `/tmp/loopper-040-candidate-wal-focused.log`。此补充只修改测试与记录，标准成品内容不变，最终远端完整门禁验证包含该修正的提交。

## Windows 启动器测试调用修正

运行中 Windows 日志进一步显示 `BundledLauncherTest` 把带空格的批处理路径直接作为 `cmd /c` 首个命令，并同时传入带空格参数。CMD 的引号处理让它在真正执行脚本前尝试运行截断的 `...\bundle`，因此返回 1。日志 `/tmp/loopper-040-windows-progress.log` 保留。

测试改为通过 CMD 的 `call` 调用同一个批处理，仍保留跨工作目录、带空格路径与参数、包内 JDK 优先级和退出码 17 的端到端断言。缺少 JDK 的用例除退出码外，增加实际启动器的 Java 缺失错误断言，避免命令解析失败被误认为预期拒绝。启动脚本本身未修改。

`./scripts/dev-check.sh backend BundledLauncherTest` 在本机 macOS 的 2 项检查通过，日志 `/tmp/loopper-040-launcher-focused.log`；Windows 原生行为以修正提交的远端 CI 为准，未用本地通过冒充 Windows 通过。
