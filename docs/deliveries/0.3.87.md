## 问题与根因

2026-09-08，CupXml2Java 任务 `ea609184-4117-4f4a-a761-1fec83b255bc` 在没有撰写 Session 的情况下进入双评审。实际执行策略为 `SERVER_DOCUMENT_MATERIALIZATION`，服务端将 REQUIREMENT 的 snapshotMarkdown 转换为文档块，直接写入 `docs/detail-design.md`；唯一验收断言只是需求快照标题的 TEXT_EXISTS。文件为 81 行、8743 字节，尚未包含要求的详细设计正文。两位 Judge 均返回 REVISE，任务停在 WAITING_INPUT / JUDGE_REVIEW_NOT_APPROVED。

前端还有两处关联证据缺失：overview 未投影阶段尝试计数，audit 合并没有重新绑定 Stage.attempts；差异摘要 SQL 只识别 DIFF，遗漏服务端实际持久化的 GIT_DIFF，任务头部又只从 verifier.changedPaths 计数。

## 修改

- 新 Markdown/DOCX 文档任务使用 `DOCUMENT_AUTHORING / OPEN_CODE_IMPLEMENTATION`，正式 Start 后创建撰写 Session，按冻结需求读取授权资料并写出完整交付文件。保留现有 Session、预算、路径、重试、取消和停止证明边界。
- 简单与多章节文档共用该执行路径，不再把需求快照转换成成品 artifact_plan；需求中的二级标题也不再被直接当成最终章节包或限制为 2–6 章。历史冻结的服务端文档计划继续使用原 materializer 恢复；表格转换保持原流程。
- 原生格式验收要求可解析的非空文本和有效本地链接，新增 TEXT_NON_EMPTY 断言及完整前后端协议往返。独立 JUDGE 条件逐项核对冻结需求、实质内容与事实来源，明确需求稿、提纲、写作计划不能代替正文。非空/结构检查不声称证明语义完整。
- 文档执行提示明确撰写职责、事实核对、写入范围和真正 DOCX 格式要求，不修改代码/配置/测试或执行无关构建。
- overview 返回已持久化的阶段计数与冻结角色/执行信息；audit 和后续 overview 刷新均重新绑定阶段尝试列表。
- DIFF/GIT_DIFF 均投影允许的变更路径等摘要字段，保持正文按需读取；头部文件数优先使用任务基线差异。
