# 文档模板任务合同

本合同持有模板第二期的需求开发与需求代码评审行为。第一期 `CODE_REVIEW`、`CONTRIBUTION_REPORT` 的版本 1–7 继续按[既有模板合同](seven-feature-contract.md#内置模板任务)恢复。文档模板独立冻结版本 `1`，不能使用第一期报告任务的测试豁免、日期范围或完成策略。

## 输入、身份与文档

目录按模板声明 `workflow`、输入能力与执行策略。`REQUIREMENT_DEVELOPMENT` 使用项目当前目录；`REQUIREMENT_CODE_REVIEW` 使用冻结分支代码树。两者一次接收 1–10 份 DOCX、Markdown 或文本 PDF，单文件最多 20 MiB、整批最多 50 MiB；保留解析器的解压、页数、提取量和单次解析时限。旧 DOC、宏、加密、损坏文档或扫描件不能冒充可解析输入。图片、流程图等未提取信息必须展示局限，不宣称全文理解。

`POST /api/template-tasks/document-runs` 接收 multipart 的 JSON `metadata` 和多个 `files`。metadata 包括 `requestKey`、模板 ID/版本、项目 ID，以及仅评审需要的分支 ID。开发入口继承项目；全局入口选择项目。评审不要求日期或对比分支。写接口验证 `X-Loopper-Local-UI: 1`、输入与冻结版本；发起身份以完整元数据、文件名和原始内容哈希确定。相同请求键和内容返回原记录，改变内容则冲突；响应丢失不得制造第二次业务。

发起记录先于 Designer/Task 存在。上传保存原文件、解析版本、表示哈希、分段标题/位置/哈希与提取局限；全部原文件落盘并核验后写入 upload-ready。中断上传只能用同一请求与原文件补齐。未完整上传不得开始分析。文件和分段按所属发起记录读取，路径 containment、符号链接、敏感文件及身份哈希校验不可省略。文档正文不塞入普通需求正文或附件表示上限。

开发与评审模型只按索引和需要读取分段。文档、代码、模型输出均为不可信数据，不能改变角色权限、调用范围或自动授权。分段已处理表示处理覆盖，不能替代语义无遗漏的独立复核。

## 需求清单与候选

需求分析师输出功能、规则、权限、异常、约束和可观察验收场景。每项需求保留原文 file/section 及逐字摘录；每个输入分段必须归属需求、背景或提取局限。多文档没有隐含优先级，相同要求可以合并但保留全部引用，冲突进入待处理项。

原文复核者独立读取分段和其他相关文档，检查遗漏、无依据新增、错误合并和错误引用。仅候选 JSON 合法不表示语义正确；服务端能确定的引用、覆盖、范围和身份错误直接拒绝。语义问题形成修正候选，文档本身的未决事项保留在 `issues`。

候选种类为 `DOCUMENT_REQUIREMENTS_V1`、`DOCUMENT_REQUIREMENT_REVIEW_V1`、`REQUIREMENT_CODE_ASSESSMENT_V1`、`REQUIREMENT_ASSESSMENT_REVIEW_V1`。使用独立 `DOCUMENT_TEMPLATE_MODEL_RUN` 所有者、项目作用域及角色专属 MCP，不接收自由文本完成声明。创建计划、精确消息 ID、提示哈希和候选版本在 I/O 前冻结。完整替换、幂等重放、同 Session 修正、未知投递查询和停止证明按 [OpenCode 合同](opencode-contract.md)执行。

需求按有界批次提取及复核，所有批次持久化后才公开新清单版本。开发前真实业务待决阻断设计；用户逐项回答后创建新的分析版本，重新提取及独立复核。旧清单和原始文档保留，回答历史可按版本读取。开发或恢复不能用项目重析覆盖已冻结的设计、执行或证据。关联设计后的问题沿用设计详情和原执行恢复入口，不能以普通全自动模式代替用户业务回答。

## 需求开发

模板发起授权覆盖冻结范围内的需求整理、单包或大型流程选择、确认设计、正式 Start 和测试。服务端通过仓库事实选择技术角色，明确软件开发意图，不让通用 Router 把输入文档判为文档写作。

先尝试普通单包设计。只有服务端证明现有阶段容量不能安全表达时，才在停止原角色后晋升既有大型滚动流程；保留原模型用量、预算、包数与阶段容量限制。范围扩大、真实业务冲突、危险权限请求必须等待用户。

设计有效前不创建执行 Task 或 Stage。开发采用当前目录执行机制：Git 项目由正式 Start 创建任务分支，未提交文件进入既有文件处理入口；不自动 stash、删除或提交用户文件。项目目录租约、基线漂移、第二 writer、暂停、取消及重启按 [架构合同](architecture.md)和现有目录执行合同处理。模板协调等待不意味着执行停止，不释放仍有阻断义务的租约。

单包与滚动包通过既有 Designer、工作包批准、Task Start、Implementation、验证器和双评审执行。模板专属自动动作不放宽普通 Designer 的人工边界，也不启用自动采用推荐业务答案的策略。

每包必须包含实际可执行的行为测试。最后一包必须显式绑定模板约束 `POLICY-FINAL-REGRESSION`，执行跨包、受影响功能及核心业务流程回归；该编号是服务端授权约束，不伪装为上传文档原文。需求到批准场景、实际 Stage/Attempt/验证结果的映射在报告前冻结。

开发报告要求本轮正式验证通过、全部阶段测试证据和同批需求/风险双 Judge PASS。文件存在、构建成功、模型声明或单 Judge PASS 不能替代该证明。执行成功后仍由用户在 Task 详情独立处置结果，不自动认定失败结果通过，不自动提交、推送、合并或发布。报告完成与 Task `AWAITING_DECISION` 分别呈现；后者未处置或仍持有租约时不得通过模板归档隐藏。

Task 首次关联时冻结其文档来源；剩余包计划另外冻结本版需求清单和哈希。新实施 Session 依据 Stage 所属包计划或 Task 来源读取原文，不能因为发起记录的需求版本变大就读取新内容。验收映射包含需求版本、清单哈希与是否适用于当前需求；同编号的新规则不能复用旧规则的测试证据。已撤销或合并的旧需求证据保存在历史映射中，不计为新版需求通过。

滚动 Stage 创建时绑定确切的执行合同修订、合同内阶段位置和设计稿来源。物理阶段序号可以包含失败与已替换的历史，不能作为新版计划数组下标。编译按具体设计稿和修订定位，重复使用 WP 编号不能复用旧计划的编译结果；末包约束固定在原计划版本内。最终报告按已冻结成功事实中的阶段核验，失败历史仍可查看，不计入新计划通过项。

`GET/POST /api/template-tasks/document-runs/{id}/supplements` 提供补充预检与 multipart 上传。补充文档追加存储，与原文一起重新提取和复核，不按文件名或上传时间决定覆盖顺序。上传前保存幂等身份、预期 Task/包版本、原文件序号和目标分析轮次，原文与补充合计保持 10 份和 50 MiB 限额；原文件未完整保存时不启动分析，刷新后可用同一身份和原文件补齐。

尚未生成 Task 的设计等待允许补充文档。先保存原设计、任务设置和目标修订身份；复核完成后通过既有重新打开需求协议证明旧角色停止，再创建新版设计，保留原角色预算和技术配置。分析中断也能先完成该停止协议再恢复，新旧来源不相互覆盖。已开始执行的冻结工作包不能原地改写；执行失败继续使用已有恢复或安全剩余包重规划入口。

滚动补充复用既有成功事实点和剩余计划安全入口。只在服务端确认 writer 和设计角色已经停止、当前成功事实点可校验时接受；已冻结包不修改。新版清单有业务冲突时在需求清单回答；清单复核后通过既有剩余计划候选编译与确认入口生成后续版本。规划创建信息与消息哈希在 I/O 前持久化，未知送达先查询，取消需本地在途调用结束和远端停止证明。规划尝试与超时采用冻结预算，失败不得无限生成新计划。

## 静态需求代码评审

冻结用户选择分支的目标 SHA，读取该 SHA 的代码树，不读取用户未提交工作区，不逐个遍历历史提交。功能实现可以早于近期提交、由名称不同的入口或共享组件提供；只根据历史存在、文件名命中或检索无结果不能判定当前实现。

按功能组定位入口，追踪相关前后端、业务、数据、权限、状态、并发、共享依赖及测试源码。冻结文件目录、内容读取和检索有明确分页/行数/字符边界，缓存键包含本次快照与 blob 身份。缓存内容不替代本角色的授权或独立读取凭据。

第二期静态评审不运行构建、测试或项目脚本，不修改代码，不提供自动修复或全仓库质量扫描。结论固定为：

| 结论 | 含义 |
| --- | --- |
| SATISFIED | 当前冻结代码证据支持符合需求 |
| PARTIAL | 需求的一部分已有实现，其他部分缺失 |
| INCORRECT | 已有实现存在可说明的需求偏差 |
| NOT_IMPLEMENTED | 已检查必要入口及相关范围，有缺失依据 |
| UNDETERMINED | 歧义、冲突、读取范围或证据不足，无法判断 |

每个确定性结论必须附实际读取的冻结代码、blob、行号和摘录。`NOT_IMPLEMENTED` 另需已检查范围和必要入口缺失说明；搜索没有命中不是缺失证明。文档歧义不阻断整份评审，相关项为无法判断。测试状态固定保留 `NOT_RUN_STATIC_REVIEW`，源码覆盖和本次未执行分别展示，不从旧报告推断本次测试成功。

问题分确认缺陷、验证缺口和改进建议，附需求引用、触发条件、影响及建议，同根因合并。缺测试或风格偏好本身不等于行为错误。独立评审者覆盖全部需求结论及问题，重点复核符合需求、未实现和高严重程度结论，并读取同轮其他批次核对矛盾。候选证据必须由复核者独立读取后才能批准。

报告完成表示已处理范围和结论完成校验；发现缺陷可以正常完成报告，存在未知项或实现偏差时不能显示全部满足。预算不足保留未完成范围，不能转化为通过。

## 进度、恢复、列表与报告

`DocumentTemplateState` 与 Task、Designer、Stage、Attempt、Session、Judge 状态独立。分析中可按准备、整理、复核、设计、开发、评审、复核评审和生成报告展示；等待、停止、取消和完成必须来自服务端。所有写入采用版本校验和持久化身份，不以 UI 投影制造执行事实。

详情入口从上传开始稳定，关联 Designer/Task 后提供原设计及执行详情入口。overview 只包含状态、文档元数据、数量和关联身份，不下载正文；需求清单分页，单项、原文与报告正文按需读取。SSE 只发失效提示，断线后 REST 快照权威，刷新/重启不重复发起。迟到响应不得覆盖其他任务或新需求版本。

统一列表按持久化模板来源筛选，发起记录与关联 Task 一次业务只展示一行。筛选、搜索、分页、状态计数和归档使用同一视图；报告完成后仍保留 Task 待处置状态。关联 Task 归档及恢复同步模板行，模板归档需先检查关联执行的终态和租约。

需求分析时限、内容修正、恢复次数与执行期的 Designer/Task 预算分开。执行恢复不能重新激活旧文档分析尝试。暂停模板协调不伪装为远端停止；取消先持久化意图，确认活动文档角色、Designer 及 Task 写会话停止后才结束。未知投递不盲重发，未知停止不启动重叠 writer。

静态评审报告包含总结、需求矩阵、逐项结论和问题明细；开发报告复用需求索引并附正式执行证据和用户澄清。制品按需求版本冻结、哈希校验、作用域读取，支持预览、同版链接及整包下载。第二期不新增故事统计配置，第一期及历史绑定保持兼容。

## 验收证据

模拟 Provider 验证协议与编排，人工标注样本验证分析合同，真实模型试跑另列效果证据。源码/测试、完整 JAR、活动 JVM、浏览器与真实 Provider 互不替代。实际进度和未覆盖项记录在[第二期实施账本](deliveries/template-phase2-plan.md)，完整交付遵守[开发与交付](development.md)。
