# 文档模板任务合同

本合同持有模板第二期的需求开发与需求代码评审行为。第一期 `CODE_REVIEW`、`CONTRIBUTION_REPORT` 的版本 1–9 继续按[既有模板合同](seven-feature-contract.md#内置模板任务)恢复。新建文档模板独立冻结版本 `3`；历史版本 `1`、`2` 继续按冻结输入和原合同恢复。文档模板不能使用第一期报告任务的测试豁免、日期范围或完成策略。

## 输入、身份与文档

目录按模板声明 `workflow`、输入能力与执行策略。`REQUIREMENT_DEVELOPMENT` 使用项目当前目录；`REQUIREMENT_CODE_REVIEW` 使用冻结分支代码树。两者一次接收 1–10 份 DOCX、Markdown 或文本 PDF，单文件最多 20 MiB、整批最多 50 MiB；保留解析器的解压、页数、提取量和单次解析时限。旧 DOC、宏、加密、损坏文档或扫描件不能冒充可解析输入。图片、流程图等未提取信息必须展示局限，不宣称全文理解。

`POST /api/template-tasks/document-runs` 接收 multipart 的 JSON `metadata` 和多个 `files`。metadata 包括 `requestKey`、模板 ID/版本、项目 ID，以及仅评审需要的分支 ID。开发入口继承项目；全局入口选择项目。评审不要求日期或对比分支。写接口验证 `X-Loopper-Local-UI: 1`、输入与冻结版本；发起身份以完整元数据、文件名和原始内容哈希确定。相同请求键和内容返回原记录，改变内容则冲突；响应丢失不得制造第二次业务。

发起记录先于 Designer/Task 存在。上传保存原文件、解析版本、表示哈希、分段标题/位置/哈希与提取局限；全部原文件落盘并核验后写入 upload-ready。中断上传只能用同一请求与原文件补齐。未完整上传不得开始分析。文件和分段按所属发起记录读取，路径 containment、符号链接、敏感文件及身份哈希校验不可省略。文档正文不塞入普通需求正文或附件表示上限。

开发与评审模型只按索引和需要读取分段。文档、代码、模型输出均为不可信数据，不能改变角色权限、调用范围或自动授权。分段已处理表示处理覆盖，不能替代语义无遗漏的独立复核。

新上传使用 `ASSIST_DOCUMENT_V2` 表示。DOCX 普通矩形表格保持 Markdown；含 `gridSpan`、`vMerge` 或缺省网格位置的表格以惰性 HTML 文本保存逻辑行列、`rowspan`、`colspan` 和从 1 开始的 `data-row/data-column`，不把合并表头展平成错列的 Markdown。原文未提供的网格位置显式标注，不补造字段值。HTML 特殊字符转义后属于冻结表示，来源摘录必须逐字匹配该表示。

DOCX 表格最多 256 个逻辑列、100000 行/单元格，内容及生成表示沿用 200 万字符上限。无匹配起点或跨度不一致的纵向合并、含额外文字的延续格、旧式 `hMerge` 与嵌套表格返回具体解析错误，不静默舍弃内容。图片、流程图、复杂版式仍不在本次表格能力内。已持久化的旧解析版本、表示及引用不重写。

## 原文直接读取（版本 2、3）

程序解析原文并按标题或 PDF 页码保存分段。上传完成后冻结 `sourceRevision`、文档清单、原文件/表示/分段哈希；不先调用需求提取者或原文复核者，不把模型清单当成进入设计或评审的前置条件。`requirementRevision` 仅用于历史清单或新版静态评审产出的结果矩阵，与原文版本分别存储。

原生 MCP Resource 模板为 `loopper-document://{role}/{scope}/{file}/{section}`。开发 role 使用签名的会话许可，评审 role 使用当前受限模型运行身份；目录、按段原文和读取凭据与同名 Tool 服务共用授权。客户端不能直接读取 Resource 时，使用 `read_document_resource` 或角色专属文档读取 Tool；不能绕过版本、项目、角色、运行代际或冻结文件校验。目录分页不返回正文，原文首次展开或被模型请求时读取。

需求开发上传后直接进入 `DESIGNING`。索引中的 `DOC-n` 只是原文件来源，模型结合原文、代码和项目规范形成正式设计及可观察验收场景；源文件名不作为仓库写入路径。原有设计编译、包容量、Start、目录租约、正式测试、最终回归与双评审继续生效。最终两位评审员均需读取本版全部原文章节后才能判 PASS，报告前再次验证读取证据；读取范围完整不等于语义理解完整，评审必须主动对照原文检查设计遗漏。

静态评审上传后直接进入 `ASSESSING`，按连续原文章节有界分批（每批最多 48000 字符、256 个分段）。评审过程形成 `DOCUMENT_CODE_ASSESSMENT_V2`：每条同时给出需求描述、原文位置、待澄清事项和实现结论；无需复制原文摘录或维护双向段落台账。程序从选定原文位置生成报告引用。无评审要求的分段给出 `skippedSections` 理由；每个分配章节均须有结论来源或跳过说明，不能无声遗漏。

`DOCUMENT_CODE_REVIEW_V2` 独立重新读取本批原文、补充引用和被跳过章节，复核结论及代码，并检查跨批次矛盾。遗漏修正可以直接引用原文章节，无须先有需求编号。只有全部批次及独立复核完成后才发布结果矩阵；矩阵不回写或替换原文。新旧候选都保留完整替换、同 Session 修正、幂等、未知投递与停止证明规则。

遇到无法提取的图片或流程图，先继续正文阅读与设计；缺失信息影响实现或验收时再提出具体问题。静态评审继续可判断部分，受影响条目保留 `UNDETERMINED` 和待澄清事项。解析器局限不得被当成没有业务要求，格式或引用校验不能证明语义无遗漏。

## 历史需求清单与候选（版本 1）

需求分析师输出功能、规则、权限、异常、约束和可观察验收场景。每项需求保留原文 file/section 及逐字摘录；每个输入分段必须归属需求、背景或提取局限。多文档没有隐含优先级，相同要求可以合并但保留全部引用，冲突进入待处理项。

原文复核者独立读取分段和其他相关文档，检查遗漏、无依据新增、错误合并和错误引用。仅候选 JSON 合法不表示语义正确；服务端能确定的引用、覆盖、范围和身份错误直接拒绝。语义问题形成修正候选，文档本身的未决事项保留在 `issues`。

提取候选的 `sources` 与 `coverage.requirementKeys` 必须双向一致：每个引用都对应一项分段归属，每个分段关联都由该需求的真实引用支持；背景和提取局限不可携带需求编号。拒绝回执定位需求编号与 `fileId:section`，不回显原文内容。角色提示要求从引用反向生成覆盖，不以删除有效需求或放松逐字校验来解决错误。

候选种类为 `DOCUMENT_REQUIREMENTS_V1`、`DOCUMENT_REQUIREMENT_REVIEW_V1`、`REQUIREMENT_CODE_ASSESSMENT_V1`、`REQUIREMENT_ASSESSMENT_REVIEW_V1`。使用独立 `DOCUMENT_TEMPLATE_MODEL_RUN` 所有者、项目作用域及角色专属 MCP，不接收自由文本完成声明。创建计划、精确消息 ID、提示哈希和候选版本在 I/O 前冻结。完整替换、幂等重放、同 Session 修正、未知投递查询和停止证明按 [OpenCode 合同](opencode-contract.md)执行。

需求按有界批次提取及复核，所有批次持久化后才公开新清单版本。开发前真实业务待决阻断设计；用户逐项回答后创建新的分析版本，重新提取及独立复核。旧清单和原始文档保留，回答历史可按版本读取。开发或恢复不能用项目重析覆盖已冻结的设计、执行或证据。关联设计后的问题沿用设计详情和原执行恢复入口，不能以普通全自动模式代替用户业务回答。

## 需求开发

模板发起授权覆盖冻结范围内的需求整理、单包或大型流程选择、确认设计、正式 Start 和测试。服务端通过仓库事实选择技术角色，明确软件开发意图，不让通用 Router 把输入文档判为文档写作。

先尝试普通单包设计。只有服务端证明现有阶段容量不能安全表达时，才在停止原角色后晋升既有大型滚动流程；保留原模型用量、预算、包数与阶段容量限制。范围扩大、真实业务冲突、危险权限请求必须等待用户。

设计有效前不创建执行 Task 或 Stage。开发采用当前目录执行机制：Git 项目由正式 Start 创建任务分支，未提交文件进入既有文件处理入口；不自动 stash、删除或提交用户文件。项目目录租约、基线漂移、第二 writer、暂停、取消及重启按 [架构合同](architecture.md)和现有目录执行合同处理。模板协调等待不意味着执行停止，不释放仍有阻断义务的租约。

单包与滚动包通过既有 Designer、工作包批准、Task Start、Implementation、验证器和双评审执行。模板专属自动动作不放宽普通 Designer 的人工边界，也不启用自动采用推荐业务答案的策略。

每包必须包含实际可执行的行为测试。最后一包必须显式绑定模板约束 `POLICY-FINAL-REGRESSION`，执行跨包、受影响功能及核心业务流程回归；该编号是服务端授权约束，不伪装为上传文档原文。需求到批准场景、实际 Stage/Attempt/验证结果的映射在报告前冻结。

开发报告要求本轮正式验证通过、全部阶段测试证据和同批需求/风险双 Judge PASS。文件存在、构建成功、模型声明或单 Judge PASS 不能替代该证明。执行成功后仍由用户在 Task 详情独立处置结果，不自动认定失败结果通过，不自动提交、推送、合并或发布。报告完成与 Task `AWAITING_DECISION` 分别呈现；后者未处置或仍持有租约时不得通过模板归档隐藏。

Task 首次关联时冻结其文档来源；剩余包计划另外冻结本版来源和哈希（版本 2 为原文版本，版本 1 为需求清单）。新实施 Session 依据 Stage 所属包计划或 Task 来源读取原文，不能因为发起记录的需求版本变大就读取新内容。验收映射包含来源版本、哈希与是否适用于当前需求；同编号的新规则不能复用旧规则的测试证据。已撤销或合并的旧需求证据保存在历史映射中，不计为新版需求通过。

滚动 Stage 创建时绑定确切的执行合同修订、合同内阶段位置和设计稿来源。物理阶段序号可以包含失败与已替换的历史，不能作为新版计划数组下标。编译按具体设计稿和修订定位，重复使用 WP 编号不能复用旧计划的编译结果；末包约束固定在原计划版本内。最终报告按已冻结成功事实中的阶段核验，失败历史仍可查看，不计入新计划通过项。

`GET/POST /api/template-tasks/document-runs/{id}/supplements` 提供补充预检与 multipart 上传。补充文档追加存储，不按文件名或上传时间决定覆盖顺序。版本 2 冻结新的原文版本后直接重做未执行设计或剩余包规划；版本 1 保留重新提取和复核流程。上传前保存幂等身份、预期 Task/包版本、原文件序号和目标分析轮次，原文与补充合计保持 10 份和 50 MiB 限额；原文件未完整保存时不启动分析，刷新后可用同一身份和原文件补齐。

尚未生成 Task 的设计等待允许补充文档。先保存原设计、任务设置和目标修订身份；新原文冻结后（历史版本 1 在复核完成后）通过既有重新打开需求协议证明旧角色停止，再创建新版设计，保留原角色预算和技术配置。分析中断也能先完成该停止协议再恢复，新旧来源不相互覆盖。已开始执行的冻结工作包不能原地改写；执行失败继续使用已有恢复或安全剩余包重规划入口。

滚动补充复用既有成功事实点和剩余计划安全入口。只在服务端确认 writer 和设计角色已经停止、当前成功事实点可校验时接受；已冻结包不修改。版本 2 的业务冲突由 Designer 原有问答处理，版本 1 仍通过清单澄清；通过既有剩余计划候选编译与确认入口生成后续版本。规划创建信息与消息哈希在 I/O 前持久化，未知送达先查询，取消需本地在途调用结束和远端停止证明。规划尝试与超时采用冻结预算，失败不得无限生成新计划。

## 静态需求代码评审

冻结用户选择分支的目标 SHA，读取该 SHA 的代码树，不读取用户未提交工作区，不逐个遍历历史提交。功能实现可以早于近期提交、由名称不同的入口或共享组件提供；只根据历史存在、文件名命中或检索无结果不能判定当前实现。

按功能组定位入口，追踪相关前后端、业务、数据、权限、状态、并发、共享依赖及测试源码。冻结文件目录、内容读取和检索有明确分页/行数/字符边界，缓存键包含本次快照与 blob 身份。缓存内容不替代本角色的授权或独立读取凭据。

第二期静态评审不运行构建、测试或项目脚本，不修改代码，不提供自动修复或全仓库质量扫描。结论固定为：

| 结论 | 含义 |
| --- | --- |
| SATISFIED | 当前冻结代码证据支持符合需求 |
| PARTIAL | 需求的一部分已有实现，其他部分缺失 |
| INCORRECT | 已有实现存在可说明的需求偏差 |
| NOT_IMPLEMENTED | 已检查必要入口及相关范围，有缺失依据 |
| UNDETERMINED | 歧义、冲突、读取范围或证据不足，无法判断 |

每个确定性结论必须附实际读取的冻结代码、blob、行号和摘录。`NOT_IMPLEMENTED` 另需已检查范围和必要入口缺失说明；搜索没有命中不是缺失证明。文档歧义不阻断整份评审，相关项为无法判断。测试状态固定保留 `NOT_RUN_STATIC_REVIEW`，源码覆盖和本次未执行分别展示，不从旧报告推断本次测试成功。

问题分确认缺陷、验证缺口和改进建议，附需求引用、触发条件、影响及建议，同根因合并。缺测试或风格偏好本身不等于行为错误。独立评审者覆盖全部需求结论及问题，重点复核符合需求、未实现和高严重程度结论，并读取同轮其他批次核对矛盾。候选证据必须由复核者独立读取后才能批准。

报告完成表示已处理范围和结论完成校验；发现缺陷可以正常完成报告，存在未知项或实现偏差时不能显示全部满足。预算不足保留未完成范围，不能转化为通过。

## 进度、恢复、列表与报告

`DocumentTemplateState` 与 Task、Designer、Stage、Attempt、Session、Judge 状态独立。分析中可按准备、整理、复核、设计、开发、评审、复核评审和生成报告展示；等待、停止、取消和完成必须来自服务端。所有写入采用版本校验和持久化身份，不以 UI 投影制造执行事实。

详情入口从上传开始稳定，关联 Designer/Task 后提供原设计及执行详情入口。overview 只包含状态、文档元数据、数量和关联身份，不下载正文；需求清单分页，单项、原文与报告正文按需读取。SSE 只发失效提示，断线后 REST 快照权威，刷新/重启不重复发起。迟到响应不得覆盖其他任务或新需求版本。

统一列表按持久化模板来源筛选，发起记录与关联 Task 一次业务只展示一行。筛选、搜索、分页、状态计数和归档使用同一视图；报告完成后仍保留 Task 待处置状态。关联 Task 归档及恢复同步模板行，模板归档需先检查关联执行的终态和租约。

需求分析时限、内容修正、恢复次数与执行期的 Designer/Task 预算分开。新文档模板冻结默认关闭的业务超时开关，关闭时批次及累计分析不因耗时自动停止；需求开发向 Designer、滚动计划与 Task 传递同一开关。历史缺失字段仍按原启用语义恢复，详见[业务超时开关](architecture.md#业务超时开关)。执行恢复不能重新激活旧文档分析尝试。暂停模板协调不伪装为远端停止；取消先持久化意图，确认活动文档角色、Designer 及 Task 写会话停止后才结束。未知投递不盲重发，未知停止不启动重叠 writer。

静态评审报告包含总结、需求矩阵、逐项结论和问题明细；开发报告复用需求索引并附正式执行证据和用户澄清。制品按需求版本冻结、哈希校验、作用域读取，支持预览、同版链接及整包下载。第二期不新增故事统计配置，第一期及历史绑定保持兼容。

## 验收证据

模拟 Provider 验证协议与编排，人工标注样本验证分析合同，真实模型试跑另列效果证据。源码/测试、完整 JAR、活动 JVM、浏览器与真实 Provider 互不替代。实际进度和未覆盖项记录在[第二期实施账本](deliveries/template-phase2-plan.md)，完整交付遵守[开发与交付](development.md)。

## 模板批次并发窗口

版本 2、3 的需求代码评审以及第一期版本 8、9 的代码评审、贡献报告使用每任务并发窗口。全局设置 `limits.templateAnalysisConcurrency` 默认 4，允许 1–16；启动参数为 `LOOPPER_TEMPLATE_ANALYSIS_CONCURRENCY`。新任务冻结设置，历史版本和已有运行不随设置变化。需求开发固定为 1，继续原有工作包与目录写入规则。

窗口在独立批次之间生效；创建中、准备发送、送达未知、运行中和停止中的批次持续占用名额。批次完成后独立补位，结果按原始序号汇总，不因完成顺序变化。贡献者分析等待所依赖的全部变更分析，静态评审独立复核等待分析完成，最终汇总等待全部所需结果。失败候选和已验证兄弟批次分别保存；恢复仍要求原有停止证明与预算，不在未知会话上叠加重发。并发不扩大工具权限或免除最终内容校验。

前端从原文上传开始展示真实状态、原文版本、可展开的章节和实际运行批次数。新版需求开发不展示空的前置需求清单，静态评审矩阵在结果生成后展示。历史清单、报告下载、任务列表来源与已关联 Task 的独立结果处置保持兼容。

## 模型导航与参数预检（版本 3）

沿用原文直读，不增加前置需求编译。`get_document_review_work(runId,offset,limit)` 返回本批原文章节、读取状态、已有评审条目编号和目录工具指引，每页最多 100 条；目录为集合查询，不读取正文，不将章节标题当成需求。`get_development_task_guide(scope)` 返回已签名角色的冻结目录、阶段目标、交付物和路径许可；尚未形成 Stage 时不虚构目标文件，不扩大写权限。

所有内部候选提交入口共用 `describe_submission_contract(runId,pointer)`。服务端按已授权候选身份选择提交工具，从实际注册工具取得 JSON Schema；空 pointer 返回完整结构，JSON Pointer 返回指定嵌套字段。返回当前 revision、字段类型、必填项、枚举与已有字段说明。运行、所有者和代际校验沿用正式提交；角色不能指定其他角色的 Schema。只读合同查询不算第二个提交入口，旧的冻结权限清单保持有效。完整参数说明不代替原文、代码证据或业务校验。

新版冻结模型输入保存 `interactionVersion=1`。直接评审的 `snapshotSha` 可填 null，由服务端绑定冻结代码 SHA，再按绑定后的规范候选保存；显式不同 SHA 拒绝，历史 input 的缺省 interactionVersion=0 仍要求原 SHA。`issues` 只表示业务规则歧义或冲突，非空时结论须为 UNDETERMINED；代码证据缺口写 assessment.limitations 或 VALIDATION_GAP，不能通过删除真实歧义来通过校验。

`check_document_review_candidate` 与正式提交共用生产校验，返回具体字段路径、遗漏章节和业务待决/结论冲突。它只预检，不创建候选回执、不推进状态、不消耗正式提交次数；仍受当前角色工具调用与时间预算限制，重复失败应先查询结构并修正。只有正式提交接受、远端停止证明及后续独立复核才能产生结果。

## 批次失败与手动重试

第一期模板任务与文档评审版本 3 将已经证明终止的“模型失败、未提交有效结果”保存在对应批次。第一期连续长度停滞也按批次处理。其他独立批次继续按冻结窗口推进，成功结果保持不变；报告仍等待全部必需结果，失败不得折算为通过。发送或停止身份未知不属于可直接重试的终止证据。

独立批次失败后不自动重新触发，先记录并释放窗口名额，继续执行本阶段剩余批次；创建中、发送未知、运行中或停止中仍占用窗口，不能按失败跳过。全部独立批次结束后集中展示待处理项，用户可勾选 1–100 个批次统一重新触发；一次选择在短事务内校验全部身份、版本及停止证明并创建新代次，任一项无效时整组选项回滚。成功结果不重做，未选失败项继续保留；所选批次再次失败时重新回到清单。贡献者分析和独立复核仍等待依赖结果，最终汇总等待全部必需结果验证通过，不把未选失败项当作完成。需求开发不使用此并发恢复策略。

每次重试创建新的批次/模型尝试和远端 Session、消息及候选身份。第一期 V109 保留原批次全部输入、错误、提交回执和续接记录，使用 generation 选择当前批次；统计不重复计入旧代次。历史第一期任务同样将已证明终止的模型失败、缺少有效结果及长度停滞局限到当前批次，不改变冻结模型、输入、并发窗口、预算或评审合同。旧版整任务暂停留下的、尚未创建会话的 STOPPED 批次不列入失败清单；用户恢复任务后按原冻结输入自动接续这些未执行批次，保留旧记录。

第一期选择入口为 `/api/template-tasks/{taskId}/batches/retry`，文档评审入口为 `/api/template-tasks/document-runs/{id}/batches/retry`，请求 `batches` 含每项 `id/expectedVersion`；单项 `/batches/{batchId}/retry` 入口保持兼容，沿用相同校验。待处理项通过同范围 failed-batches 接口按时间加 ID 游标分页，列表不加载正文；`facets.retrySelectionReady` 为服务端的本轮选择就绪标记，前端不能从当前页是否有失败推断可重试。执行期间只显示已记录失败的提示，完成后展开选择清单。文档评审就绪判断还要覆盖尚未创建模型会话的全部冻结原文章节，不能把当前窗口为空当作全轮完成。

手动重试不清零累计时限、总预算、取消或停止证明。旧运行尚未停止、任务总预算/时限等待、已取消或过期的原文/评审轮次拒绝启动。模型会话终止只是执行状态，正式候选、静态结论、独立复核和最终报告仍分别验证。
