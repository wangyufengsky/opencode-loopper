## 固定分支代码的公共采集基础

- `GitCommitReader` 提供独立于 Spring 的固定 Git 读取，`GitCommitSnapshots` 保留旧入口的事务边界。分支解析与指定提交采集分开；调用者先持久化准确提交，再在数据库事务外取回单个提交。采集使用独立受管裸仓库，子项目只列出其固定目录树，不检出分支、不读取暂存内容、不运行项目脚本。已经取回的对象可以在来源暂时不可用时按原提交重新读取。
- `GitSnapshotInventory` 统一有界 Git 文件清单与原有敏感路径判断。符号链接、子模块、受保护文件和超限文件保留明确限制，截断或重复目录记录直接拒绝。原需求代码评审、快照审查及源码路径策略已有真实调用者；需求代码评审仍持有自己的冻结身份、短事务和完成语义，历史 JSON 与数据库迁移不改写。
- `GitSnapshotJobs` 准备不可变输入及内容寻址的独立 Java helper，`GitSnapshotWorker` 先保存准确提交选择，再取回私有对象；`DurableCommands` 仍须先持久化监督进程身份，再发执行许可。跨重启复用请求和回执，缺失停止证明保持停滞。Git 采集不能使用“无外部工作”证明。完整私有快照恢复不重新查来源或解密凭据；远程采集的临时凭据只在进程环境中传递，保持项目/全局与准确服务器绑定。
- `system.repository.snapshot` V1 复用命令适配器，`WorkflowRepositoryContract` 和 V173 保存节点级来源及只写一次的清单；结果、停止证明、清单、接受交付和节点收尾同事务完成。`WorkflowRepositoryRecords` 及 `WorkflowSourceFiles` 校验生产者与固定清单，通过既有 HTTP/MCP 文件读取交付 `REPOSITORY_SOURCE` DOCUMENT。静态代码资料不取得 writer CODE 权限。
- 预设“固定分支代码”已可添加到画布；公共分支输入按需搜索、分页和明确选择，不自动使用当前/默认分支。节点详情显示提交、限制、失败恢复与执行记录。专用需求代码评审的分批、实际阅读和报告组合已接入下述新流程，真实 Provider 等价验证仍待完成。

## 当前版本审查的公共采集基础

- `GitReviewReader` 提取原快照审查的完整证据算法，原 `SnapshotReviewEvidence` 已实际调用。日期增量沿用第一父链与北京时间边界，全面审查沿用冻结分支 tip；最终树比较、子项目空树、重命名/删除、排除范围和 V1/V2/V3 初始证据策略保持原合同，不改写历史快照。
- `GitReviewJobs`、`GitReviewWorker` 通过既有 `DurableCommands` 执行独立受管 Java helper，完整代码与 Git 历史采集均在数据库事务外。首次执行许可后才固定准确提交、项目范围和采集时间；失败重试保持该选择，成功对象可在源仓库离线时重新核验。凭据只在准确服务器绑定的临时环境中传递。
- `GitReviewJobProtocol` 显式区分全面与日期增量，全面模式拒绝日期；`GitReviewEvidenceCodec` 以流式不可变格式保存版本、树、全部文件、单元及初始引用，最多 320,000,000 字节、单字段 4,000,000 字节、单集合 100,000 项。保留原算法的 64,000,000 字符代码材料上限，超限失败，不截断交付；拒绝截断、尾随字段、非法 UTF-8、路径链接和原记录被替换。
- `system.review.snapshot` V1 已接入持久化命令、V181 不可变来源账本及原子接受；全面和日期增量两个预设复用同一适配器。`WorkflowGitCaptures` 统一路由分支、历史和版本采集，停止未知、取消后迟到及事务回滚沿用原命令合同。
- `WorkflowReviewContent` 将概况及逐单元正文保存为受管文件，`WorkflowReviewRecords` 复核成功生产者、停止证明与接受摘要；HTTP/MCP 复用固定文件列表/正文接口。原仓库与私有 Git 丢失后仍能读取，内容损坏明确拒绝。画布已接入范围/时限、分支/日期、采集报告与按需文件查看。
- 来源节点及通用后继读取已有真实 Git、SQLite 和 Fake OpenCode 证据；专业分析及条件问题复核见下节，用户确认完整分批及报告组合见“完整固定版本审查组合”。现有入口保持可用，不把 helper 或来源节点成功等同于业务审查完成。

- `SnapshotReviewClaims` 由原 `SnapshotReviewProtocol`、`SnapshotReviewReads` 和新 `WorkflowSnapshotContract` 共用，覆盖 V1/V2/V3 的既有候选语义。新流程仅创建 V3 专业输入，原任务恢复策略不变。
- `WorkflowSnapshotEvidence` 从已接受文件重建精确资料，`WorkflowSnapshotInputs` 核对来源及显式分析/复核依赖，`WorkflowSnapshotPreparation` 在模型创建前完成事务外准备。V182 保存固定输入、完整分页、12 次不同关联请求与当前角色代码引用，停止/取消守卫均留在原模型协议。
- `WorkflowSnapshotReads` 提供目标/基线目录、单文件搜索及有界行读取；对象摘要、排除范围、当前尝试与停止状态逐次核验。内容缓存不共享角色阅读授权，搜索不作为正式引用依据。初始输入与关联查询分别计量，不对原模型 Token、耗时或费用增加限制。
- 新增 `snapshot.analyze`、`snapshot.review` 两个预设并复用 `builtin.snapshot-review` 的专业说明和 `WORKFLOW_READ_ONLY` 能力上限。分析的两个业务结果支持显式条件分支；复核与默认业务验收仍由用户自由组合。
- 中文配置及交付视图已接线，展示文件位置、候选问题、片段覆盖和独立判定。完整分批、完整报告及作者追溯已组合，按需阶段报告和 V3 保守复用仍待接入，不以单节点验证代替全模板等价。

- `workflow/WorkModule` 区分工作定义、角色绑定、输入合同、输出合同和完成条件。`BuiltinWorkModules` 持有 2 个源码设计模块及 6 个文档分析模块。

- `ImmutableContentStore` 保存有界、按内容哈希寻址的文件；真实调用者为原源码快照和新源码文档交付适配。既有源码目录不迁移，数据库先保存身份再写文件；损坏对象不覆盖，文件 I/O 不在数据库事务内。
- `SourceWorkDeliveries` 从已持久化的源码文档元数据生成 `WorkFileManifest`，读取绑定项目、生产者、整份清单哈希及文件 ID。部分发布不能消费；用户导出副本不作为输入来源。此适配保持旧 SQLite 正文，尚未把既有大字段迁往文件系统。

## 节点执行基础

- 普通目录由 `WorkflowDirectoryPreparation` / V162 固定基线，`WorkflowDirectoryWorkspaces` 接入原 writer 工作区生命周期，V163 保存结果清单和 SEED/RESTORE 应用记录。`WorkflowDirectoryMutations` 持有节点应用账本并调用 `WorkflowDirectoryTransform`，只恢复本次固定前后版本，`WorkflowDirectoryStorage` 保存不可变字节；用户项目不初始化 Git。正式 Start、MCP 候选、CODE 接受、原目录恢复及租约交接共用既有链路，实际 Provider 资格仍待验证。

- V143 独立保存节点运行、计划到节点的不可变绑定、尝试、接受交付、停止证明及本计划的公共输入。计划可以在未来版本引用相同的未变节点；执行尝试始终持有原输入版本。
- `WorkflowNodeRuns` 只持有短事务和状态审计。一个节点至多有一条非终态尝试；交付接受不推动完成，终态需要停止证明，成功还需要已接受结果。历史输入、交付与停止记录不可改写。
- `WorkflowNodeInputs` 读取本计划内已完成生产者，批量装配有名称的输入，固定尝试 ID 和交付哈希；公共输入按计划版本冻结。它不查询“最新工作结果”，也不拼接整段模型会话。
- `WorkflowReadiness` 区分仍在等待、可以执行和条件未选中的节点。技术失败不选择成功分支；并行汇合等待所有适用前置节点，未选分支允许省略对应可选输入。
- `WorkflowNodeActions` 已有人工节点的实际执行适配：显式开始、等待人工输入、提交结果、停止证明、下游固定输入，以及所有适用节点完成后结束需求。此入口只承接人工文本、结构化结果和控制记录，不调用模型或隐藏 Judge。
- 节点摘要与尝试输入/交付正文分离，正文查询校验需求、节点和尝试归属。两个人工操作接口要求 local UI 标记、幂等键和版本；同一请求并发重放只创建一次尝试。

只读模型、文件工作和执行控制现已接入同一账本，范围见后文；运行中计划修订已接入，各类适配器的验证证据保持独立。

## 只读模型节点

- `free.readonly` V1 以 `WORKFLOW_READ_ONLY` 适配槽运行明确选定角色修订的专业说明。当前支持文本、JSON、业务决定、控制结果和一份候选计划，以及交付即完成或指定业务结果的完成规则；代码、文件和程序验证使用专用适配。
- Start 在事务外核定项目真实路径，在短事务中复核项目版本、节点资格与输入，冻结角色和尝试，写入 V144 模型运行。此时不创建 Session；只读节点不占用 writer Queue/Lease。
- 创建计划、Prompt 和消息 ID 持久化后，由有界后台任务推进创建、发送与观察。创建回执或发送回执丢失时，按原创建身份和原消息精确查询；不凭本地超时重新创建。每次外部调用返回后复核当前身份与版本。
- 模型通过 `get_workflow_node_work` 查询任务及输入名称，通过 `read_workflow_node_input` 分页读取固定输入，通过 `submit_workflow_node_result` 提交结构化交付。输入分页不拆开 Unicode 字符；模型不能按任意记录 ID 读取其他节点。CODE 输入通过 `list_workflow_input_files` 和 `read_workflow_input_file` 按名称读取固定清单及 UTF-8 文件；文件游标绑定交付摘要，二进制文件通过所属输入/输出的 HTTP 下载入口读取。未知文件属于可修正的查询错误。历史冻结会话不会自动增加新工具。
- 内存签名的调用范围绑定运行代次、需求、尝试、Session 和消息；传输层加入身份通知，SQLite 中冻结的业务 Prompt 不保存调用范围凭证。精确恢复核对正文及身份通知，不接受修改、重复或缺失身份的远端消息。
- 权限基线只开放授权的原生只读工具及该节点的五个私有工具。角色仍可进一步收窄；当前不开放外部 MCP、统计命令、旧候选提交、写入、Shell 或未接入此适配器的辅助知识工具。后续知识适配须先冻结相应资源授权。
- MCP 校验未知字段、类型、必需输出、业务结果、版本和幂等键。可修正的提交错误不结束尝试；交付接收与请求回执同一事务保存，失败整体回滚。接受结果还须等待独立终态或确认停止，才能完成节点和释放后继。

## 不可变代码交付基础

- V146 分开保存代码快照意图和完整清单。读取 Git 和写文件前先冻结节点尝试、需求、项目、输入摘要、工作区指纹及基准/结果 tree；所有文件校验后才发布清单。中断重试使用同一组对象，不能换成新的 HEAD 或当前目录。
- `GitCodeSnapshots` 直接读取固定 Git 对象，保留二进制字节、可执行权限和基准相对的增删改。登记项目为仓库子目录时，只交付项目内文件，仓库其他目录的变更使整份交付失败。受保护路径、符号链接和子模块保持阻断，不静默省略后声称交付完整。
- 文件按 SHA-256 写入受管 `workflow-code` 内容存储；清单由 SQLite 保存。读取每个文件校验清单身份、大小和摘要，不回退到当前源码文件。单文件上限 4,000,000 字节、单项目 10,000 文件及 128 MiB；Git 单次和整批读取均有明确时限。
- 内部冻结入口要求当前写入尝试、同一租约与独立停止证明。发布前再次复核尝试版本和目录身份；晚到结果不能给已结束的尝试补成果。清单存在不表示节点完成；只有本尝试接受的 CODE 引用且节点成功，才允许作为交付读取。
- CODE 值使用程序生成的版本、快照 ID 和完整清单摘要，拒绝模型伪造目录或引用其他尝试。清单保留准确输入血缘；重复捕获验证原内容，不替换损坏的受管对象。
- Git 和普通目录均已由下节节点工作区调用。普通目录 CODE 在 V163 记录私有对象库，原目录继续作为租约身份；只接受本工作区已固定的结果树。实际写入 Session、固定输入的 MCP 文件分页及 HTTP 下载共用原链路，画布沿用固定文件清单与下载。

### 固定代码改动与可复用提交对象

- `WorkflowCodeFiles.changes` 与 HTTP `/changes` 先解析路径中的需求、节点、尝试及命名输入/输出，再读取已接受的不可变 CODE 清单；复用原来源与停止边界。按路径分页，游标同时绑定清单摘要与 `changes` 类型，不读取当前 checkout 或完整正文。`WorkflowCodeChanges` 在节点详情按需显示中文增删改和对应版本下载。
- `GitFixedCommits` 从固定树、可选父提交、作者、时间和正文形成确定性 Git 对象，重新计算 SHA-1/SHA-256 并核对存储字节。普通目录原有基线/结果快照已经复用此实现，旧固定元数据仍生成同一提交；不使用当前暂存区或工作区文件。
- 引用创建复用 Git 的 `start/prepare/commit` 事务，在 Git 持锁后再次拒绝直接或悬空符号引用；发生检查冲突时 `abort` 释放锁。重复恢复只接受同一引用的同一提交，不移动已有不同对象。进程、输入输出和等待有界，使用既有停止证明及事务外 Git 入口。
- 需求成果选择由 `WorkflowPublicationReads` 持有；明确本地提交及恢复由 `WorkflowPublications` / `WorkflowPublicationExecution` 持有；远端独立确认与受监督推送由 `WorkflowPushes` / `WorkflowPushExecution` 持有。普通目录由 `WorkflowWritebackReads` / `WorkflowWritebackPreviews` 进行三方清单检查；`WorkflowWritebacks` 保存独立确认，`WorkflowWritebackLeases` 参与共享 FIFO，`WorkflowWritebackFiles` / `WorkflowWritebackExecution` 负责原备份、OS 操作锁、固定文件转换和最终原子交接。预览不能产生已提交或已回填事实。

## 固定文件的程序检查节点

- `WorkflowVerification` 定义 `system.verify.files` V1 的有界配置：一份必需 CODE 输入，1–16 项内容精确/包含、哈希或文件移除检查。SYSTEM 节点不携带角色、Session 或模型权限；固定输出为检查说明与 JSON 报告，业务结果为通过/未通过。

- `WorkflowVerificationCoordinator` 从持久化运行记录恢复，最多四项并发检查。没有外部副作用的重算沿用原尝试；最终报告、停止证明、终态、检查点与控制结算同事务，写入失败不提前完成。它不创建模型会话、写入队列、租约或影子 Task。

- `WorkflowControls` 接受单步、运行至节点、连续执行及暂停命令，保存幂等回执、模型选择、控制/需求版本及确认的检查点。`WorkflowDispatch` 只计算必要依赖闭包、就绪节点和剩余重试资格；不调用模型或改写业务状态。
- `WorkflowDispatchCoordinator` 从持久化 ACTIVE 记录恢复工作，最多四个需求并行，单个需求不重叠派发。每轮最多准入四个节点；writer 仍使用原共用队列、目录检查和停止证明。旧手动 Start 不得绕过已经建立的执行控制。
- `WorkflowSettlement` 根据实际终态收束条件跳过、范围完成、等待、耗尽和最终完成。交付接受不能提前释放依赖，已准入节点不会因用户暂停而丢失。人工节点的提交完成相当于确认；工作节点配置执行后暂停则保存独立检查点，待用户逐批明确确认。
- 检查点确认与控制更新/回执原子提交，旧确认不能清除新检查点。技术失败按累计尝试次数决定是否自动重试；用户单步重试仅授权明确的下一序号。暂停后的旧准入凭证、未知停止、悬挂会话均保持阻断。
- 控制 API 位于 `/api/workflows/requirements/{id}/control`；写入口要求 local UI 权威。当前验证使用文件 SQLite、受控模型、真实临时 Git 与调用层集成，需求执行画布已接线并完成受控 HTTP 夹具的浏览器检查；真实 Provider 验收仍未完成。

## 需求创建与执行画布

- `/requirements` 提供分页需求列表；从流程库选择使用流程，或从 `/requirements/new` 选择项目与确切模板修订，创建独立计划并进入画布。主页、任务和历史设计的新建入口已统一迁入；旧 `/designer` 无历史会话时转入新入口，有明确或已保存会话时继续历史流程。需求开发模板表单已退出新建目录，历史上传记录及恢复服务保留；其他专业模板入口分别保留其兼容资格。
- 规划期间可以调整节点、连接、公共资料声明和布局，保存计划与确认独立；确认后仍需明确选择单步、运行至节点或连续执行。执行期间图定义只读，布局单独保存；运行中修改剩余计划须先暂停派发，按上文修订合同保存并重新选择执行方式。
- 节点详情按需读取分页尝试、冻结角色/任务、固定输入、已接受交付物和受管 CODE 文件；人工节点提交结果，模型节点可停止或恢复原尝试。当前日志为有界只读观察，不是生命周期事实。
- 控制与执行摘要由 `WorkflowRunReads.snapshot` 在同一只读事务提供；模型日志通过 `WorkflowRunActivity` 在数据库事务外读取并复核 Session 身份。普通摘要不加载提示、资料或交付物正文。
- 写操作和部分保存保留原幂等键与回执；读回失败不重复提交，过期读取不覆盖新选择。检查点绑定成功尝试，需要用户明确确认。

## 持续执行边界

1. 工作模块目录只描述已有能力；节点运行另外持有定义版本、冻结角色版本、输入引用、尝试身份、停止与完成记录。
2. 新调度器用独立节点尝试身份，通过明确适配器调用角色执行；复用现有 Session/候选协议，不能用前端状态驱动旧 Task 生命周期。
3. 模板创作、需求计划和执行记录三者分开。完整节点定义在开始尝试时冻结；已完成输出不因画布删除而物理清理。
4. 写目录的开发节点保留 Queue/Lease 与受管工作区。只读角色可并发；自由节点依然经过角色权限、路径和输入可用性校验。
5. 新自由任务的结果合同、MCP 工具及模块版本必须一起接线后才能进入可选目录。不能把任意已有角色名称当成可直接运行的模块。

## 原生命令验证执行基础

- `WorkflowCommandVerification` 和 `WorkflowCommandContract` 定义明确版本、固定 CODE 输入、直接 argv、测试用途、时限与报告语义。`WorkflowCommandWorkspace` 按既有内容快照重建独立目录，恢复部分准备时核对原字节；实际检查不能触碰当前项目 checkout 或受管输入对象。
- `WorkflowCommandParser` 在计划候选反馈、人工应用和运行准入间共享定义校验。普通脚本用 CHECK，声明 TEST 则必须是支持的测试框架；规划允许空 argv 占位，运行仍拒绝空命令。错误候选可以在原模型尝试内修正，不先接受错误计划再等执行失败。
- `DurableCommands`、JDK-only 监督程序和有界二进制协议持有不可变请求、监督身份、执行许可、停止请求及最终回执。监督程序可在主服务退出后继续运行；同一作业登记后不再启动第二个命令。后台进程身份不可确认或回执缺失保持未知，不以进程 PID 数值或输出存在冒充停止。
- V155 追加命令执行账本和独立生命周期；扩展停止证明时保留旧证明及模型创建守卫，并重建依赖停止表的代码/候选守卫。`WorkflowCommandStore` 只处理短事务，`WorkflowCommandExecution` 在事务外处理文件及进程。报告/证明/节点/命令/控制一起提交，失败恢复原回执。
- 调度按系统模块分流；`WorkflowExecutionGuards` 统一判断模型或命令的恢复阻断。命令读取、停止、恢复及原始证据 API 校验原尝试作用域，本地写操作沿用权限、版本和幂等。后台扫描最多四个作业，并避免同一次检查的 I/O 重叠。
- V154 补齐 SYSTEM 节点成功后的真实人工检查点。原实现只允许 WORK，不能据此宣称上一批程序节点的暂停已生效；本次以末节点不完成、明确确认后完成的实际回归修正这一缺口。
- 命令预设已进入目录，专用表单分别编辑程序、独立参数、输入代码、用途、时限及输出要求；空命令需要按项目配置，不提供虚假的通用默认值。系统节点固定交付物以简洁摘要显示。
- 运行摘要投影命令状态、版本及恢复原因，正文只在执行记录展开时读取；服务端校验冻结请求和结果摘要，并保留监督进程身份。画布使用命令自身版本停止/恢复，保留未知回执和原幂等请求；过期证据不会覆盖当前尝试或较新读取。报告区区分检查未通过、超时、输出不完整与停止未知，执行记录不把零退出码单独当作通过。
- 配置保存重开、失败报告、执行记录、恢复和停止回执重试已通过 Chrome 的显式 HTTP 夹具验证，三种皮肤和 390px 窄屏截图已查看。原生进程证据来自本机 JDK，不能代替 Windows、真实 Provider 或完整 JAR 运行验收。默认开发组合见下节；专业模板及最终交付继续按持续计划推进。

- `GitHistoryReader` 是旧历史模板与新独立 helper 共用的完整证据算法；`TemplateGitEvidenceCollector` 保留旧事务适配，算法不依赖旧 Task 或工作流生命周期。原历史规范继续由[功能合同](seven-feature-contract.md#内置模板任务)持有。
- `GitCommitReader.captureHistory` 与单提交树采集分开：前者要求完整历史、拒绝浅仓库并验证可达对象；后者保持原浅快照行为。明确来源、项目子目录范围及对象格式共用已有守卫，抓取精确提交前已保存选择。
- `GitHistoryJobs` 在事务外准备请求和不可变输入；`GitHistoryWorker` 只有取得原监督进程许可后才执行 Git。取消、重启、后代停止和未知状态沿用 `DurableCommands`，不能因文件存在推导节点成功。生产节点接线仍须先持久化业务意图，独立验证停止，再接受交付。
- 完整证据保存在 `workflow-git-history/{nodeId}/evidence`，不放入普通 128 KiB 节点结果。新流式传输上限为 320,000,000 字节、单字段 4,000,000 字节及每集合 100,000 项，仍保留原总补丁/提交边界；超限拒绝。逐字段保留原始身份、共同作者、排除依据和补丁，无源仓库也能从完整私有历史重验既有字节。
- 此处仅为已验证的执行基础；尚未注册历史节点预设，也未建立 DOCUMENT 来源账本与后继阅读/分批/报告接口。检查点 48 已完成下述节点接线；历史专业分析/贡献/报告仍须独立组合，不能把旧历史 Task 整体包装成单节点或称作迁移完成。

## 历史专业分析节点
