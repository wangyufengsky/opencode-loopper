## 失败原因与保留边界

1. 一次来源复核仍可能生成格式不符或内部矛盾的冻结模型。9 次运行停在来源未确认，既不能继续候选修复，也不能冒充用户遗漏需求。当前来源失败保留原始材料和错误码，不增加复核次数；这一停止策略限制了通过率。
2. 布尔或枚举抽象会丢失粒度。`buffer_flush` 一份方案只声明缓冲仍非空，不能证明全部缓冲保留。`stable_key_merge` 两份方案只表达单项状态，不能证明混合批次中任一冲突导致全批次不变。SAT 可以证明这些较弱模型的内部一致性，无法自动证明它们忠实于原文。
3. `atomic_import` 的部分方案未区分历史成功与当前解析/验证；把 NOT_RUN 当作动作前输入也不能保证动作后没有解析。另有正确方案明确表达历史成功、相同内容及不再解析，说明不是案例本身必然不可解决。
4. 复杂度启发式漏掉 `config_precedence` 三次运行，仍走普通 V2；本次不根据独立验收集追加关键词。新流程只覆盖无需包内提问的复杂修订，原生/文本问题修订仍保持原路径，不在用户答复前冻结义务。
5. 普通候选仍有字段、范围和验证能力表达问题。此次固定 JSON 示例降低部分格式错误，但不能把错误码数量下降当作语义质量提升。

后续改进应另建训练样本，优先使模型明确区分项与批次、前值与后值、历史事实与当前动作，并把不足的抽象标为尚未确认。若调整来源错误恢复预算，需另行确定回合边界；本版本不擅自增加用户授权的一次独立复核。独立验收语料保留为历史回归，不能再次当作未见验收集。

## 适配器修正与 GEPA

已知案例试运行暴露两个离线适配器问题：跨 JVM 的无序 scope JSON 导致哈希不同；拼接模型进度消息与最终消息导致复核 JSON 无效。分别使用稳定排序及 Codex `--output-last-message` 修正，生产冻结上下文本身不受前一问题影响。保留 R1/R2/R3 试运行证据，不混入最终 72 次统计。三个独立 JVM 的范围提示已验证相同。

GEPA 状态为 `BLOCKED_AT_ADAPTER_VALIDATION`，额外优化请求 **0**。当前 Codex 接口缺少已验证的真实 Provider 请求发起前预算拦截能力；回合用量和会话次数均不足以落实 200 次真实请求上限，因此没有运行优化器，也没有生产在线 GEPA 依赖。

另以历史 6 个业务待决与 6 个权限/约束冲突案例运行生产来源预检：12/12 正确阻断，无候选、无模型请求。它们是确定性回归，不能称为新独立样本的模型分类准确率，也不计入设计成功率。
