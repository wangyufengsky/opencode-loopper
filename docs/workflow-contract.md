## 模板、计划与执行

流程模板定义可复用工作结构、参数和默认完成规则；需求任务持有本次目标、项目与授权。
创建需求任务时形成独立流程计划，模板后续修订不改变已有任务。
流程计划的业务修订、画布位置、节点执行与模型 Session 分开。拖动画布不改变依赖或使运行失效。
模板编辑的图与布局分别使用版本校验保存；回执未知时重试原命令及原键，不换键重复创建。部分保存成功后保留原回执继续剩余保存。版本冲突保留本地草稿，用户可另存或明确放弃后读取最新版本。
用户将计划另存为模板时需参数化任务特定资料；不复制执行身份、凭证和历史成功状态。

另存时可选结构，默认保留当前画布的步骤及未保存调整；也可选择本任务首次节点尝试所用的计划修订，恢复当时的通用规划结构。后者不以最初模板代替执行前的用户定制，也不自动混入后续节点；未执行任务只能选择当前步骤。两种方式均先展示实际图、节点差异、公共输入声明与配置诊断，再由用户确认保存。具体路径、章节和任务文字按所选定义保留，新任务重新提供公共资料；上传引用、冻结代码版本、交付正文、尝试、成功状态和本次目标均不自动带入。

保留当前步骤时，仅对当前计划中有已应用候选证明的程序分批节点（源码设计、源码单测、原文评审、历史分析和版本审查 V1）转换：保留节点身份、输入、前后依赖、重试和检查点，改为无角色的人工“确认固定步骤”，不再次自动展开已经保存的批次。预览明确展示这些转换；若规划输出仍被其他节点绑定或存在自定义结果分支，拒绝静默转换，提示先调整输入/分支或选择首次执行结构。未应用的规划和模型设计节点保持原定义。

服务端校验源计划修订及预览内容摘要，运行状态推进本身不会使同一计划的保存失效。创建独立自定义模板、不可变源计划记录和幂等回执使用同一短事务；失败整体回滚，回执未知重放同一键和原内容，已完成回执优先于后续计划版本检查。V177 记录模板初始定义与源需求/修订/摘要/保存方式的对应关系，不将来源记录作为新任务输入。另存不修改原需求计划、公共资料、控制模式或尝试。页面在回执未知时保留原命令并阻止换内容另存，保存成功后留在原任务，可明确打开新流程继续编辑。

工作节点包含角色、任务、输入绑定、预期输出与完成规则。预设工作模块与自由任务使用同一合同。
系统节点不需要虚构 AI 角色；由明确版本的程序适配器执行，保存检查、路由或汇合等必要结果。人工确认使用独立人工节点。
业务角色配置决定提示与能力声明，实际能力仍受模块适配器、项目策略与冻结任务授权限制。

预设目录保存带版本的节点初始内容及输入槽位，读取时解析推荐角色的具体修订；添加到画布后复制完整节点，用户可继续修改任务、角色、输入和完成规则，不依赖可变目录在执行时补内容。列表分页只返回摘要，正文和角色版本按需读取。选择节点交付物作为输入时同时建立显式依赖；资料已移除或类型变化时拒绝添加，不静默换成其他来源。选中预设、添加节点、保存计划均不自动开始执行。
内置流程由配置组合这些预设，通过内部发布入口追加不可变修订；重复发布相同配置不产生修订。已有需求及自定义副本保持原定义和角色版本；公共编辑接口仍不能改写或删除内置流程。当前目录包含四十五项预设和十二条内置组合，覆盖默认开发、源码设计与单测、原文评审、知识整理、历史审查及贡献报告，以及全面或日期增量版本审查组合。具体模块及专业模板的适配范围见模块清单；目录存在不代替完整运行资格。

## 图与输入

默认树状排版，语义为支持分叉、汇合的有向无环图。重试属于节点尝试，新一轮修复也可形成新节点。
依赖边决定执行先后，输入绑定决定使用哪些成果；后者可引用多个可用上游节点的已接受交付物。
输入引用必须对应显式依赖可达的上游或本次需求的公共资料，不允许隐式依赖未结束节点。
条件分支依据结构化业务结果选择路径；未知/缺失结果保持阻断，不能默认为成功。
画布使用中文业务结果名称，节点 `outcomes` 保持稳定条件键；`parameters.outcomeTitles` 保存键到名称的 JSON 映射。模型查询收到冻结参数，按名称理解含义并用原键提交，修改显示名称不改变连接和完成条件。
未选路径为不执行；汇合只等待适用路径，普通并行汇合等待所有选中前置工作。
没有额外依赖的同级节点具备并发资格，资源守卫决定是否能实际并发。共享目录的 writer 不重叠。

## 交付物

每个成功完成的工作节点有交付物；失败也可产生部分成果和诊断，但不能当作成功结果。
交付物具有不可变身份、版本、所属需求/节点/尝试、内容摘要、生成时间、输入版本血缘与接受记录。
用户展示名称与内部稳定 ID 分开。正文、文件清单和实际文件版本能够重建，不引用“当前目录”冒充快照。
SQLite 持有正文或文件清单以及业务身份；大型文件可存受管目录并由摘要校验。
读取必须校验任务归属和冻结输入授权。资料内容不构成模型新的权限或指令。
开始尝试时绑定精确输入版本；任务公共上下文与上游成果共同构成输入，不默认拼接全部聊天历史。

新尝试的上游 TEXT、JSON、DECISION、CONTROL、PLAN 输入保存固定输出引用：生产节点运行身份、生产尝试、输出名称、整份交付摘要、该输出规范化 JSON 的 SHA-256 与 UTF-8 字节数。正文继续由原不可变交付持有，不在每个消费者的输入快照里重复复制。CODE、DOCUMENT 沿用已有受管文件引用；需求公共资料仍按原规则冻结。包含输出引用的输入快照为 V2，历史 V1 内联快照原样保留并继续读取、恢复及重试，不修改已有迁移或记录。

读取引用只按已固定的生产尝试和输出名称查询；必须属于同一需求及生产节点、尝试成功且存在停止证明，并核对整份交付、输出类型、正文摘要与长度。缺失、损坏或身份不一致明确失败，不能回退到当前计划、最新尝试或项目当前文件。替换后续计划与生产节点后，历史消费者仍能读取原版交付。重试比较完整的固定输入语义，兼容旧内联快照与新引用格式。

输入元数据接口返回引用及来源，正文由独立 HTTP/MCP 接口按明确输入名称读取，每页最多 12000 个 Unicode 码点，使用 UTF-16 字符偏移并避免拆分代理对。单项读取只加载该生产尝试，内部汇总使用集合查询。专业复核仍须通过自己的 MCP 完整读取全部绑定稿件，页面阅读不代替角色读取证据。画布首次展开输入只读取元数据，正文由用户逐项展开、按页继续；中断重试原位置，切换尝试时丢弃旧响应。

输入快照仍受 2 MiB 限制，普通交付 128 KiB、源码设计与原文评审包装 300 KiB 及专业正文 256 KiB 的限制不变；引用传递解决累计正文重复存储，不扩大图、单节点输入或单份交付容量。

AI 通过结构化 MCP 提交业务结果，程序绑定身份并校验语义。候选提交接受、运行停止与业务完成是不同事实。
同键同内容返回原回执；同键异内容、旧版本、跨作用域和旧运行代次不能改变新状态。
后续节点仅消费已满足其输入要求的接受结果；程序校验、停止与完成条件未满足时不得提前释放依赖。
上游更新产生新版本，已消费旧版本的下游保留原血缘，要求复核、重做或新增修改节点。

## 上传的需求原文

公共资料声明支持 DOCUMENT。用户在需求画布选择 DOCX、Markdown 或文本 PDF，每次 1–10 份，单份不超过 20 MiB、合计不超过 50 MiB；复用 `ASSIST_DOCUMENT_V2` 解析器及既有格式、路径和原文件完整性检查。解析后的阅读文件合计不超过 64 MiB，超限完整拒绝，不截断为成功资料。图片、版式等解析局限随资料显示，不把扫描 PDF 当成已读取正文。

上传由本地页面显式发起，先在短事务中保存需求归属、计划修订、幂等身份、原文摘要、解析版本、章节及清单，再在事务外保存并校验原文件，最后记录不可变的可用事实。V172 新增独立上传、阅读文件和可用记录；上传不创建 Task、模型 Session 或节点尝试。保存中断可从上传历史取回原身份，按原顺序补传同一批原文件；相同键不能换内容或目标。取消、计划修订变化或公共资料冻结后不能使未完成上传变为可用；已完成上传的同键重放只返回原结果。

用户明确选择已保存资料，正式 Start 将 `UPLOADED_DOCUMENTS` 固定引用写入公共输入快照。上传历史不会被自动选择为最新版本，不跨需求复用身份。原文、解析内容、清单摘要和既有消费者不会随重新上传而变化；确认计划不自动执行。需求未开始前可更换选用的资料；执行后的资料仍从原尝试输入读取。

节点继续用现有私有文件 MCP 的绑定名称获取文件目录和分段正文，不接收模型指定的任意上传身份。目录包含 `manifest.json`、原文件和按文档顺序/章节序号组织的 Markdown 阅读文件，清单保存原文件、解析表示摘要、章节数量和解析局限。章节标题和正文保留在阅读文件中；原文件按原始字节下载。HTTP 预览和模型读取均验证需求/项目归属与固定摘要，模型读取返回前复核活动身份。公共 DOCUMENT 校验不允许手填 JSON 冒充已完整保存的上传；节点生成的 SOURCE、CODE、DESIGN_DOCUMENT 仍走各自既有生产者与停止资格。

这条链路提供文档类工作模块的固定输入。默认开发流程将需求原文声明为可选公共资料，并绑定到需求提问和设计节点；没有上传时仍可使用文字需求。专业评审、独立复核及完整分批报告见下文；其历史模板入口的替换须分别具备相应资格，不从默认开发通过推导全部专业模板等价。

## 固定分支代码资料节点

`system.repository.snapshot` V1 是无角色的 SYSTEM 节点。必需的 `branch` TEXT 输入明确选择本地分支或远程及分支引用；画布公共输入可搜索和分页选择，但不自动选择默认分支。开始采集时才定位提交，不把选择分支或确认计划视为已经冻结代码。`repositoryTimeoutSeconds` 为 10–600 秒，默认 180 秒。

V173 先保存节点、需求、项目、原分支、原项目路径及输入摘要。独立监督任务持久化请求和进程身份后才授权子进程；子进程先不可变保存准确提交、仓库归属及子项目范围，再读取私有裸仓库对象。重试沿用同一节点的已定位提交，不跟随分支移动，也不混入工作区未提交内容。已完整采集的对象可在来源离线时重新验证，恢复不重新请求凭据；原私有证据缺失或损坏保持阻断，不能以当前代码替换。需要新提交时新增采集节点。

本地采集不请求账号；远程 HTTP(S) 使用注册项目的全局/项目账号规则和准确服务器匹配，临时授权仅传给监督进程及受控 Git 子进程。请求、固定来源、清单和回执不保存账号密码、认证头或远程 URL。账号变化不改写已固定来源。Git、网络和文件 I/O 在数据库事务外；监督进程丢失且无终态回执时保持停止未知，不盲目重启。

成功输出 `REPOSITORY_SOURCE` 类型的 DOCUMENT 固定引用、JSON 采集报告和 TEXT 说明；失败保存明确报告且不输出可用代码资料。完整清单最多 50000 项，包含 Git 对象摘要、模式、字节数和读取限制；受保护文件、符号链接、子模块和超过 2 MiB 的对象不开放正文。采集成功表示固定提交与完整清单可用，不表示其中每项都可阅读，更不表示业务审查通过。该静态资料不作为 writer 的 CODE 基线。

收到真实成功回执后，程序再次检查本尝试身份与版本；V173 清单、结果、COMMAND_TERMINAL 停止证明、接受交付和节点结束在同一短事务内完成，任一失败整体回滚。用户提前取消后返回的成功回执仅用于停止收尾，不再接受资料；未启动使用 COMMAND_NOT_LAUNCHED，不能伪造 NO_EXTERNAL_WORK。

后续节点按固定输入名称使用已有文件 HTTP/MCP。读取校验同项目/需求、具体成功生产者、停止证明、清单摘要和 Git 对象原字节，不回退到“最新版本”。文件界面区分可读对象与限制项；Git blob 摘要通过 `blobSha` 表示，不冒充原文件 SHA-256。画布展示代码来源、准确提交、项目目录和限制统计，内部 Java 启动参数仅在主动展开执行记录时显示。

## 固定版本审查资料节点

`system.review.snapshot` V1 是无角色的 SYSTEM 节点，提供“固定日期增量代码”和“固定全面审查代码”两个可编辑预设。`reviewMode` 为 `DATE_INCREMENTAL`（默认）或 `FULL`；前者明确绑定分支、开始日期、结束日期三个 TEXT 输入，后者仅绑定分支。日期、第一父链与最终树比较沿用[冻结版本代码审查合同](snapshot-code-review-contract.md#输入与版本)，非法范围在创建尝试前拒绝。`reviewTimeoutSeconds` 为 10–600 秒，默认 600 秒。

- 正式 Start 后才创建 V181 节点级来源记录和持久化命令。监督采集沿用同一节点的原分支、项目路径、模式、日期及已选提交；失败重试不随分支移动，需要新资料时新增节点。全面模式固定分支 tip，日期增量固定基线和目标提交。原工作区、index、refs 及未提交内容不变，不占用 CODE writer 租约，也不启动隐藏模型。
- 来源身份、输入摘要不可改删；完整清单只能写入一次。成功命令回执、独立停止证明、清单、接受交付与节点结束在同一短事务内保存，任一失败整体回滚。文件读取、Git 和受管进程均在事务外；恢复复用原进程回执。取消后迟到的成功只参与停止收尾，不接受新资料；尚未启动和停止未知保持各自既有证明规则。
- 成功输出 `REVIEW_SOURCE` DOCUMENT 固定引用、JSON 采集报告和 TEXT 说明；失败只保留诊断，不提供可用来源。SQLite 清单最多 32 MiB，正文保存到受管内容目录：`overview.json` 包含固定版本、文件、范围及排除信息，逐单元 JSON 保留正文和完整初始引用。正文集合上限 320,000,000 字节，超限拒绝，不截断为成功；普通交付只带固定引用。
- 后继按明确输入名称使用已有文件 HTTP/MCP，列表分页、正文分段读取。读取复核同项目/需求、具体成功生产者及停止证明、接受交付和清单摘要，再验证文件 SHA-256。来源仓库及采集私有 Git 离线后仍可读取受管资料，缺失或内容变化明确失败，不回退最新分支或另一需求。
- 画布提供范围与时限配置、明确分支/日期输入、提交和采集结果。模板中切换全面模式时，仅移除无人使用的原公共日期字段；切回增量补齐所需日期。其他节点仍在使用的字段及需求已冻结的公共声明保留。失败报告隐藏残留的成功信息；同树无变化与非单调时间范围有独立说明。

采集结束表示后继可使用固定资料，不表示专业审查、问题复核或最终报告已经完成。专业工作节点及完整分批/报告组合见下节；按需阶段报告见下节，跨任务复用仍待接入；旧入口保持可用。

## 固定版本的专业分析与问题复核

`snapshot.analyze`、`snapshot.review` V1 是独立只读 WORK 节点，复用已有源码评审角色及冻结的角色版本。原模板与新节点共用 `SnapshotReviewClaims` 的覆盖、引用、问题与复核规则；不包装旧模板 Task，不增加必经规划师或后台 Judge。

- 分析使用 V3 容量分批：稳定路径及文件内顺序、最多 48000 字符/64 个片段，初始完整代码引用保留；配置 `snapshotBatchOrdinal` 从 0 开始，画布从 1 显示。排除且无代码的单元不进入模型批次，空范围/不存在批次不能创建模型会话。
- 复核绑定同一份来源和已成功、停止的分析，只分配候选引用相关的原分析片段；关联上下文按需单独读取。不含候选问题的分析不能启动复核。分析必须声明 `HAS_FINDINGS`、`NO_FINDINGS` 两个结果，程序核对结果与实际问题数量。可将“存在候选问题”的边连接到复核；固定来源可经上游可达路径绑定，无须增加绕过条件的直接边。用户仍可省略或删除业务复核。
- 每次尝试在创建 Session 前于事务外读取已接受资料，再经身份/版本复核保存 V182 不可变专业输入。输入上限 2 MiB，超限明确失败，不静默裁剪。保存后恢复不重算批次，即使原采集文件或私有 Git 离线也可使用已经保存的初始输入。
- 角色从 WORK MCP 的 `{analysis:true,offset,limit}` 完整分页获取本批输入，最多每页 12000 个 Unicode 码点；读取记录绑定尝试及输入摘要。候选接受要求完整输入已交给当前角色；上游角色的输入/代码读取不会自动成为本角色凭据。
- 关联目录、单文件搜索和代码读取继续使用文件 MCP，但要求固定目标或基线 `version`、准确路径和 `blobSha`。每次最多 200 行/32000 字符，目录最多 100 项，搜索最多 20 处有界摘要。12 个不同请求按尝试持久化并原子占位，同参数重放不重复计数；额度耗尽只能使用已有证据或记录局限。搜索不授予引用凭据。代码从私有 Git 对象读取，验证模式、排除规则、大小及 Git blob 摘要，命中共享内容缓存后仍保存当前角色的读取记录。
- 提交只填写原专业候选结构，程序绑定来源、批次、上游分析身份和展示路径。无问题结论可使用 V3 简写；缺陷必须有目标版本证据；复核须逐项覆盖候选问题，重复问题只能指向本批已支持项或明确绑定且同来源的已支持复核。候选正文沿用 200000 字符上限，专业交付包装最多 1500000 UTF-8 字节，普通模块的 128 KiB 上限不变。复核只复制问题标题，完整分析与证据仍由原交付持有。
- 候选接受与会话停止分开，取消或旧运行代次不能继续读取/提交；交付与幂等回执同事务回滚。V182 输入、分页、关联请求和代码引用记录不可改删，数据库拒绝结束后的新读取记录。
- 画布展示片段覆盖、触发条件、候选问题、源码引用、证据支持/不成立/待确认/重复等结论，内部尝试和片段编号不直接显示。无问题不等于已经独立复核，也不证明代码无缺陷；静态分析不代表测试执行通过。

这两个节点可在自定义画布中组合；完整分批、报告及作者追溯见下节。按需阶段报告见下节；符合原 V3 条件的跨任务结果复用仍需接入新流程，整体资格与旧入口替换以持续目标的最终验收为准。

## 版本分批候选与完整报告

`system.snapshot.plan`、`system.snapshot.report` V1 是无角色的程序节点，组成“日期增量版本审查”和“当前版本全面审查”两条内置流程。默认包含固定资料、分批候选、分析原型、条件复核原型和报告；可以复制后按用户需要删改。分批与报告不调用规划或总结模型，沿用现有角色执行专业分析/复核。

- 分批对完整固定资料复用 V3 的 48000 字符/64 片段容量；保留原型任务、角色修订、输入、重试和检查点，每批分析只绑定自身范围。生成候选后停止新节点派发，用户查看、编辑或确认后才能应用，应用后仍需选择执行方式。空变化或仅排除项的候选不包含分析/复核会话，直接生成范围报告。超过完整候选或图容量明确失败，不截断代码；有复核时最多 31 批，无复核时最多 63 批，仍受 128 KiB 候选上限约束。
- 分析“有问题”结果仅连向自己的复核，“无问题”结果连向报告，复核后汇入报告。报告绑定全部必需分析及可跳过分支的复核输入；等待全部适用前置路径收束，不把资料到复核的无条件旁路当作依赖。原型存在额外消费者、重复模块或错误分支时拒绝展开，请用户调整，不擅自删除其他工作。
- 报告 `reviewPolicy=REQUIRED`（默认）要求有候选问题的每个批次完成独立复核；有效的支持、不成立、待确认与重复结论均如实记录，不将“已复核”解释为所有问题通过。用户可删除复核并明确设为 `NONE`；完整分析仍须覆盖全部资料，未复核问题作为候选保留，不能计入独立支持。完整报告节点本身也可以从自定义流程删除。
- 汇总只接受本需求、同一固定资料、已成功且停止已证明的精确分析/复核交付；缺失批次、重复批次、其他版本或未绑定的重复问题支持来源均拒绝。已接受但仍在执行的候选不能进入完整报告。覆盖、原文引用、归因、问题及局限沿用公共 `SnapshotReviewReportCompiler`；原模板任务也使用此编译器，保留原错误码和冻结恢复语义。
- 在报告派发的短事务中，V183 保存固定项目名、规范化编号、来源摘要和文件夹/主文件身份，与旧模板共用编号计数器；重复渲染、事务回滚和重启沿用同一编号。渲染与有界作者查询在事务外进行，最后原子保存 `SNAPSHOT_DOCUMENT` 清单、全部正文、交付、停止证明和完成状态。文件合计最多 64 MiB、10000 项，清单 4 MiB；失败保留固定输入，取消后不接受迟到报告。
- 作者只来自私有固定 Git 的精确版本、路径、blob 和行范围，复用已有 10 秒、4 MB、2000 行边界；只追溯问题/复核引用，不查询无问题覆盖项。仓库不可用时保留原始问题及证据，明确作者追溯不可用；不把最后修改者认定为问题引入者。页面按需读取报告、同包主子链接、单文件及 ZIP，不自动回填项目目录。
- V184 追加修正专业分析/复核的 SQLite 交付容量，使其与已有 1,500,000 字节模块边界一致；普通节点 128 KiB、原源码/原文专业模块 300 KiB 保持不变。冻结输入引用可以保存该专业结果，解析时仍核对精确的接受正文、来源身份、字节数及哈希，不复制可变“最新结果”。V1–V183 不改写。
- 当前展开步骤另存模板时，已应用的版本分批节点转为人工确认固定步骤，保留展开后的分析与条件复核；首次执行前结构仍保留可重新分批的通用配置。

跨任务 V3 保守复用尚待接入新流程。以上组合的模拟模型及真实本地 Git/SQLite 验证不替代真实 Provider 资格、旧入口迁移或最终版本交付。

## 版本分析的保守结果复用

`snapshot.analyze` V1 的 `snapshotReuse` 参数默认为 `ALLOW`；`BYPASS` 表示每次重新分析，返修或真实 Provider 资格验收须显式选择后者。程序只考虑首次尝试，且本需求不能已有失败或取消尝试；重试及已有失败后的新增替代节点均重新执行。复核节点不复用，缺少上下文记录的历史尝试继续使用原固定输入恢复，但不补建复用身份。

复用来源必须是其他需求当前有效计划中、最新且成功停止的真实模型分析：节点、尝试和模型状态均成功，具有同会话 `SESSION_TERMINAL` 证明。没有模型会话的复用结果不能再次作为来源。仅限无候选问题、无补充分组、无局限、无额外覆盖引用并完整覆盖初始片段的 V3 结论；新旧模块版本、项目、规范目录/子目录范围、完整目标及基线项目树、模型、冻结角色、任务与完成定义、需求目标、其他参数和额外文本输入都必须相同。新同树提交可以命中，单元身份重绑定到本次固定资料；任何依赖或配置变化使复用失效。

复用不削减角色权限。实际允许可变项目知识来源或其他工具能力时重新执行，即使模型尚未调用相关工具。默认版本审查角色仍具有项目知识能力，正常调用模型；用户配置的角色明确禁用该能力时，保存的项目来源清单本身不构成读取授权。允许知识能力但缺少授权快照时同样不复用；只有明确空来源绑定可按无可变资料处理。

V185 保存不可变上下文和来源回执。程序在创建会话之前、同一短事务内核对来源摘要和当前身份、接受重新绑定的交付、保存 `NO_SESSION_CREATED` 停止证明、推进尝试/节点/模型状态并执行原有检查点及调度收束。复用不伪造 MCP 阅读凭据或 Provider 调用；并发创建、取消后的迟到接受和重复派发被身份/版本守卫拒绝。事务失败保留固定输入，可从原尝试恢复。

画布显示来源需求和节点名称，并明确本次没有创建模型会话；完整报告和阶段报告保存来源名称及结果 SHA-256。原分析的无问题结论依旧未经独立问题复核，不代表代码无缺陷，也不表示执行了测试。旧任务与新节点共用无问题结论及单元重绑定规则，各自维持原冻结上下文和生命周期。

## 版本审查的按需阶段报告

固定版本资料节点成功并取得停止证明后，可在节点执行详情中按需查看、刷新和下载阶段 Markdown 报告。执行中、暂停、失败或取消后均可读取；这是查询时的观察，不保存为节点交付，不分配完整报告编号，不修改任务状态、恢复模型或启动新的工作。

- 请求明确携带需求、来源节点和具体尝试，先核对已接受的固定资料及项目归属。SQLite 的一个短只读事务捕获当前计划版本、需求状态及全部符合条件的结果，再在事务外读取固定正文、查询作者并渲染。并发执行或修改不会拼接两个计划版本；刷新才重新观察。
- 只收集当前计划绑定中最新尝试已成功、节点成功且停止已证明的 V1 专业分析/复核，必须指向相同来源尝试及摘要。已接受但尚未停止的候选、失败或取消的尝试不计完成；已移出计划的结果保留在历史详情，不计入当前覆盖。复核的分析不在当前结果中时明确说明不计入，不把另一分析的判断套过来。
- 完整固定范围始终列出已分析、尚未完成和已排除单元；多个分析覆盖同一单元时只计一次。候选问题、每个独立复核的支持、不成立、待确认与重复判断分别保留；引用的重复支持源已不在当前报告时明确标注，不补造支持。无问题结论不代表独立复核通过或不存在缺陷，目标项目测试仍显示本轮未执行。
- 复用 `SnapshotReviewPartialCompiler` 与既有固定作者查询；原模板任务继续按原代次读取，V1/V2/V3 保存结果及原复用来源说明保持可读。作者仓库离线时保留问题证据并显示不可用，已接受固定内容损坏则明确失败，不重采移动分支。
- 汇总查询次数不随结果条数增长；数据库结果正文合计及渲染正文均最多 32,000,000 字节，当前计划最多 256 项。超限明确提示分节点查看，不截断成完整结果。正文不进入 overview 或 SSE；前端只在点击后读取，切换需求/节点/尝试及卸载会中止请求并丢弃迟到响应。下载的是当前显示的同一份观察，刷新失败保留此前时间和版本。

## 固定 Git 历史资料节点

`system.git.history` V1 是无角色的程序工作，明确绑定分支、开始日期及结束日期三个 TEXT 输入。日期必须是 `YYYY-MM-DD`，按北京时间开始日零点至结束次日零点统计；结束不得早于开始。选择与日期来自本次固定输入，已开始的采集重试不能改换来源或范围，需要新资料时新增节点。

- 正式派发才创建节点级来源记录；监督进程取得许可后先保存精确分支 tip，再按同一 SHA 抓取完整历史。浅来源、对象缺失、范围超限或无法完整采集均失败，原项目 checkout、index、分支和未提交内容不变。
- 复用历史模板的证据算法，包括完整可达遍历、精确 committer 时间、固定 mailmap、原始及映射身份、共同作者、两父合并冲突基线、敏感正文排除和重复补丁依据。算法与历史兼容由[功能合同](seven-feature-contract.md#内置模板任务)持有。
- 交付包含 DOCUMENT 历史资料、JSON 采集报告和 TEXT 说明；只有完整证据保存且独立证明采集进程停止后节点成功。空范围是完整的无提交记录；采集失败保留报告和原因，不提供虚假的资料引用。
- SQLite V178 保存不可变来源、输入哈希与文件清单；完整证据及逐提交 JSON 正文保存到受管内容目录。普通交付只携带有类型的固定引用，不扩大 128 KiB 普通结果上限。新 JSON 文档集合另有 320,000,000 字节上限，清单最大 32 MiB；超限拒绝，不静默截断。
- 后继通过已成功生产者、确切需求及引用 SHA 取得文件，沿用文件列表/正文 MCP。列表仅元数据并分页，正文分段读取；不能读取其他需求、私有路径或后来更新的分支。模型停止后不再取得新读取授权，用户仍能查看已接受交付。来源和私有 Git 仓库离线后可直接读取受管正文，缺失或内容变化明确报错。
- 新节点共享现有持久化命令的停止、恢复及事务收尾。收尾失败复用原监督身份和进程结果；取消后迟到的成功结果不能接受交付。历史证据是后续分析的输入，采集成功不代表代码审查、贡献评价或报告已经完成。

## 固定历史的专业审查与贡献评价

`history.review` 与 `history.contribution` V1 是独立 WORK 节点，复用已有模板分析角色的工作说明及只读适配器。它们绑定同一需求中成功、已停止的 `system.git.history` DOCUMENT 交付，不包装旧模板 Task，不附带隐式 Judge 或规划角色。

- 审查按原 `TemplateAnalysisPartitioner` 的无损切片和分批规则选择一批；配置保存从零开始的序号，界面显示从一开始。空范围或不存在的批次明确拒绝模型分析，后续完整报告须采用无提交说明。
- 贡献评价按固定 mailmap 后的归一化邮箱选择人，稳定身份、共同作者分摊、原始/有效行数由程序从证据计算。绑定的专业审查必须已接受、成功并停止，来源摘要一致，且逐项覆盖该贡献者的全部变更；重复、跨来源、遗漏和他人证据拒绝。
- 每次模型尝试创建 Session 前，程序在事务外读取已接受的逐提交文件，计算本批输入，再经活动身份及版本复核保存 V179 不可变输入。原项目和私有 Git 不再是分析必需来源。已保存输入恢复时不重算或替换原范围；新尝试须独立准备和阅读。
- 本批输入最大 2 MiB UTF-8；超过时明确要求缩小采集范围，不截断或声称完整。WORK MCP 使用 `{analysis:true,offset,limit}` 分页，每次最多 12000 字符，沿 `nextOffset` 读完；分页记录绑定尝试和摘要。贡献者输入只含其拥有的单位及相应已校验审查。
- 候选接受只使用数据库中的固定输入及完整阅读证据，复用原覆盖、行号和身份校验。审查模型提交 `reviews`；贡献模型提交本人四维等级、理由和证据，程序绑定来源、批次、事实与上游尝试。模型不能填写来源或最终分数排名，现有独立公式仍由完整报告程序持有。
- 候选接受与远端停止分别保存；取消、停止中或旧作用域不能继续读取或提交。输入与阅读记录不可改删，事务回滚不留下半份交付；格式错误可在原 Session 纠正。
- 画布可调整批次或邮箱并查看文件、问题行、局限、四维等级。完整分批候选和固定报告由下述 SYSTEM 模块组合，生成的计划依旧先由用户确认。

## 历史分批候选与完整报告

`system.history.plan` V1 在事务外读取同一份固定历史，复用完整切片/分批及人员归属策略；不调用模型规划。内置“历史提交审查”“项目贡献周报”分别组合采集、分批、专业分析和报告节点。

- 初始形状为分批→一份审查配置→可选的一份个人评价配置→报告。程序继承用户选择的角色修订、任务说明、重试和检查点，展开全部审查批次；贡献周报仅为非机器人且有效量大于零的人员生成评价节点。每人明确依赖覆盖本人证据的审查批次，报告绑定所有审查及适用评价。

## 原文与固定代码的专业评审

`document.direct-review` V1 与 `document.direct-review-check` V1 分别承担原文代码评审和独立复核，均为只读 WORK 节点，预设使用现有需求代码评审角色。两者必需 `documents` DOCUMENT 上传资料与 `code` DOCUMENT 固定分支节点结果；复核另需 `draft` JSON 本批评审稿，可显式绑定其他批次的 JSON 稿件。原文与代码都按具体固定引用校验，不采用最新上传或当前分支。复核稿须来自同需求的成功专业评审尝试，原文、代码及代码生产者相同；主稿的批次和章节范围也必须一致。

`documentSections` 留空选择全部章节，显式设置时为原文序号和章节列表；章节从 1 开始，对应上传解析目录。每批最多 256 章、48000 字符；单个超长章节独立成批，不截断为部分范围。`documentBatchOrdinal` 为 0–511，界面显示批次 1–512，每批分配 256 个稳定需求编号。手动批次选择不能代替完整组合的覆盖验收。

角色通过原私有文件 MCP 完整读取分配原文章节，并按实际需要补充同一份原文的其他章节。原文读取使用清单 SHA-256，代码引用使用 Git blob 摘要；每次最多 200 行和 48000 字符，读取结果记录在当前尝试。确定性结论须有本角色实际读过、逐字匹配的代码引用；业务歧义保留为待澄清并使用“无法判断”。未实现结论还需已检查范围和入口缺失理由。分配章节必须有结论来源或真实未适用说明；程序校验覆盖与引用，不声称能证明语义判断正确。

作者交付 TEXT 说明和 JSON `assessment`；复核交付 TEXT 说明和 DECISION `review`。复核必须分页完整读取全部显式绑定稿件，再独立读取原文、补充引用和跳过章节；批准还须重读作者的代码引用，不能复用另一角色的读取记录。意见覆盖全部本批结论和问题，存在修正时必须返修。静态评审与复核都不运行测试，不把测试源码描述作为测试通过证据。

有效评审稿按交付完成；复核预设要求 PASS，用户可以选择有效交付即完成以保留 REVISE 并进入其他分支。取消或移除复核由用户自定义，程序不增加隐藏评审。接受交付后仍等待模型独立停止证明再释放后继。每批候选正文最多 256 KiB，节点完整交付最多 300 KiB；普通模块仍保持原上限。

V174 保存不可变的文件阅读与评审稿分页阅读记录；V175 补充需求停止范围约束。读取 I/O 在事务外，保存证据前在短事务复核当前身份及允许继续工作的需求状态。用户提前结束后，模型可完成停止收尾但不能继续读取或提交新结果。历史阅读证据、角色版本和交付保持不变。画布显示章节范围、静态结论、问题程度、原文与代码依据、局限和真实返修意见。

这两个模块可以手动组合；内置“需求原文与代码评审”已组合固定分支代码、完整原文分批候选、评审、独立复核和报告。真实 Provider 与新旧等价资格尚待验证，继续保留旧文档模板入口。

## 原文评审分批与完整报告

`system.document.review-plan` V1 是程序节点，绑定同需求固定 `documents` 原文及 `code` 分支代码，不增加 AI 规划角色。按解析后的连续分段完整分批，每批最多 256 段、48000 字符，超长单段独立成批。元数据每次最多读取 100 个章节，不加载全部正文；无法完整获取元数据或超过流程/候选容量时整份候选失败，不截取前几批。候选交付正文保持 128 KiB 上限；最多 62 批，配置独立复核时最多 31 批，其他图容量约束仍适用。

候选继承后继评审、可选复核与报告配置中的角色版本、任务、输入来源、重试、检查点和完成规则，分配不重叠的批次编号及章节。复核显式绑定全部批次稿件，报告显式汇合全部稿件与选择的意见。用户先查看确认；确认只应用计划修订，不启动节点。无法安全改写的外部稿件消费者或未说明的连接保持阻断，用户修改后再尝试。

`system.document.review-report` V1 验证本需求成功收尾的专业评审及复核交付，所有稿件必须使用同一原文引用、同一代码引用和同一代码生产者。章节分配不可重复或遗漏，批次编号与需求编号不可重复。`REQUIRED` 要求每批独立复核通过，且每次复核明确读取全部汇总稿件；`NONE` 按用户选择生成报告，保留未复核、要求修正和跨批次核对不完整的真实事实，不添加隐藏复核。删除复核节点时须明确调整报告策略。

程序复用需求报告编译器生成 `summary.md`、逐项证据、问题明细及 `matrix.json`。同根因问题按固定证据合并；原文引用最多展示 2048 字符节选并明确提示完整章节位于固定输入，不缩减评审的章节范围。解析局限、待澄清、无法判断、真实复核意见及 `NOT_RUN_STATIC_REVIEW` 保留；零条可评审需求不能被判为全部满足。生成成功、完整独立复核和需求满足是分别记录的事实。

交付类型为 `ASSESSMENT_DOCUMENT`，与详细设计文档共用不可变文件包存储及读取/下载；文件最多 1026 个、合计 64 MiB。报告正文、清单、交付、停止证明和节点完成同事务保存，失败回滚后可从原尝试恢复；取消后的迟到报告不能发布。V176 保留已有详细设计包的清单、正文与约束，并只给精确的原文分批及报告模块增加无外部工作停止资格。

Git 检查点保存会收起已跟踪和未跟踪改动，因此程序从固定 CODE 重建这部分结果，并继续对比未进入 Git 的私有文件摘要。普通目录使用固定结果与现场一致性证明。原生生成目录遵循原范围规则；源码下仅仅名为 `build`/`target` 的目录不能借此绕过。合法测试或夹具修改若未进入固定 CODE，同样不能声称交付成功。忽略文件不会为凑出干净工作区被静默删除。

范围不通过时保留固定 CODE 和失败报告，恢复工作区后才原子记录失败并释放租约。用户能在原节点查看或下载失败成果；失败 CODE 不开放给后继输入，也不改写已有成功条件。检查 I/O 无法完成则保留原尝试等待恢复，不能当作范围通过。最终事务失败可重用已保存范围证明与恢复结果；取消不接受迟到候选，停止未知不能提前交出目录。

V166 保存不可改写的私有基线、范围证明及精确 writer 阅读资格，成功守卫要求与固定检查点一致的通过证明。V167 修正范围证明对实际 `RELEASE_PENDING` 租约状态的识别；仍要求本尝试停止证明、固定检查点和同一租约持有者，不放宽写入资格。画布固定展示代码、程序范围报告和说明，仍允许用户修改角色、具体任务、重试与人工检查点。实际测试节点见下节；完整专业单测组合与场景覆盖汇总见下文。

## 原生单测执行与固定报告

`system.source.test-run` V1 是无角色 SYSTEM 节点。必需输入为 `source`、`profile`、`design` 和 `code`，必须来自同一次成功收尾的专用单测编写，且程序范围检查已通过、检查点与 CODE 一致。场景、配置及源码均验证原生产尝试与固定内容，不允许另一个 writer、模型 JSON 或同内容的不同生产者替代。模型没有直接保存测试证据的 MCP。

一个节点执行固定配置中的一个明确模块；`testModuleRoot` 默认为 `.`，多模块按各自路径分别配置，不隐式选择第一个。`testTimeoutSeconds` 为 1–3600 秒，默认 600 秒。测试命令从程序已识别的配置生成；用户或模型不能在本模块覆盖 argv。保留既有模块选择，pytest 增加 JUnit XML 输出，Jest/Vitest 增加 JSON 报告，Gradle 使用前台执行并要求重跑任务。Maven/Surefire 与 Gradle 分别读取所选模块的原生 XML 目录。报告格式按 [pytest](https://docs.pytest.org/en/latest/reference/reference.html#junit-xml)、[Jest](https://jestjs.io/docs/30.0/cli#--outputfilefilename) 与 [Vitest](https://vitest.dev/guide/reporters) 官方入口处理。

执行复用既有 `system.verify.command.v1` 持久化监督器、开始/授权/停止与恢复协议。在私有目录复现固定 CODE，不修改登记项目或固定输入；执行前报告位置必须没有既有内容，不静默删除旧报告。取得原命令停止证明后，事务外收集本次报告；每份最多 256 KiB、最多 128 份、合计最多 2 MiB，目录扫描、测试计数与读取均有边界。拒绝符号链接、外部 XML 实体、不一致计数、缺失/超限/损坏报告。报告摘要最多展示 20 个文件，完整保存的正文在用户主动查看执行记录时读取。

框架环境从本次固定 CODE 编译为同一持久化请求的准备步骤，不能临时读取当前项目或由模型追加依赖。Jest/Vitest 有 npm 锁文件时使用 `npm ci`，无锁文件时按项目声明安装并禁用锁文件写入；固定包含开发依赖。工作区子模块仅在祖先锁文件明确包含该模块时使用该祖先作为安装目录，测试和报告仍指向选定模块。已有私有 node_modules 不覆盖、不删除。Python 在本次私有目录创建 venv，使用模块或最近祖先的 requirements 文件和包声明安装测试依赖；可使用项目声明的 test/tests/testing extra，不猜测 pytest 版本或借用系统 site-packages。缺少声明或解释器时明确失败。Maven/Gradle 优先使用固定构建入口对应的项目 wrapper，再回退本机程序；wrapper 的文件与执行权限也属于固定输入。

准备与测试共用节点时限和输出预算。准备失败或准备期间取消不能启动测试，也不能通过允许业务 FAIL 的完成规则继续；服务恢复沿原请求和进程身份处理，不重新编译或安装。Jest/Vitest/pytest 报告只预建空父目录，已有报告仍拒绝。停止后重新核对原 CODE 清单中每个文件的字节、摘要和可执行权限，允许新增构建/依赖产物；原源码、测试或配置改变，即使命令退出 0、测试全部通过，也标记报告无效。新增 `inputUnchanged` 只描述本次核对事实，历史报告缺省为空，不能在界面伪造旧尝试已执行这一检查。

V168 增加不可变测试证据，将原请求摘要、原监督器结果与报告正文和摘要绑定。保存后最终节点事务失败，恢复读取已保存报告，不重跑进程，也不重新采信变化后的报告文件。新迁移仅给精确 V1 模块扩展原命令归属，成功守卫要求匹配的固定证据；旧命令和历史节点继续沿原协议恢复。取消不要求测试报告，但仍须独立停止证明，未知停止保持阻断。

通过需要完整进程结果、退出码 0、实际执行数量大于 0、无失败测试和有效原生报告。零测试、全部跳过、报告不完整、固定输入变化或执行超时不能成为有效成功。真实断言失败可按用户明确选择的 DELIVERABLES/OUTCOME 规则继续走失败分支，报告仍保存 FAIL；默认 VERIFIED 则进入失败及停滞/重试路径。跳过数量单独展示，不计为已执行。实际测试计数和关联场景列表不自动证明每个设计场景都已实现，`scenarioCoverageVerified=false` 明确保留这一边界；完整多批次规划及默认显式复核组合见下文。

本地 macOS 隔离资格已实际运行 Maven/JUnit、Gradle wrapper/JUnit、Jest、Vitest、pytest，包含 npm 工作区子模块、依赖安装失败/取消、测试修改固定配置及保存报告后的恢复。模型使用 Fake OpenCode，不能据此声明真实 Provider 或 Windows/Linux 运行资格。额外框架测试需显式设置 `LOOPPER_NATIVE_FRAMEWORK_TESTS=1`，Gradle 夹具生成还需 `LOOPPER_NATIVE_GRADLE` 指向现有 Gradle 程序；默认完整门禁不会自动触发这组联网安装资格。对应证据见持续目标的检查点 33。

`system.source.test-run` V2 支持对同一份累计 CODE 回归多批设计。仍固定 `source`、`profile`、`design`、`code`，可追加必需 JSON 输入 `design_<标识>`，每节点最多 61 批，每批至少包含所选模块的一项场景。相同设计尝试不能重复计为不同批次；不同设计尝试可以拥有同名场景，报告分批保存来源、编写尝试和场景数量，具体编号仍从各批冻结设计读取，避免大量重复正文超过报告额度。一次命令完整测试所选模块，输出 V2 报告；其他模块仍需单独节点。

程序从所选 CODE 追溯实际工作区 seed，最多 256 次继承。每一步都必须是本需求同版 SOURCE/配置下成功且已停止的专用单测 writer，范围证明、固定输入、代码清单、检查点、目录恢复与交接均须匹配。多份 CODE 输入只跟随 `workspaceInput` 指定的实际基础；依赖连线、旁路提供的代码、字节相同但生产者不同的成果不能代替继承。每批设计必须对应这条链中的编写输入。证明代码继承不等同于证明所有设计场景正确实现，仍由同版实际测试及独立复核给出证据。V1 的严格单批身份语义保持。

## 单测场景与实际测试的独立复核

`source.test-review` V1 是可选的只读 WORK 节点，默认复用需求评审员。五份必需输入为同一次成功收尾原生测试的 `source`、`profile`、`design`、`code` 和 `test`；程序追溯测试节点的冻结输入、专用 writer 范围证明、原请求和不可变原生报告，拒绝混用字节相同但生产者不同的交付。原生断言失败只有在用户将测试节点设为有效报告即可继续时才能成为下游输入；该事实不会被复核改成测试通过。

测试个案从已保存 XML/JSON 的原字节投影，稳定编号绑定报告路径、摘要和原顺序。同名参数化个案仍分别保留，通过、失败与跳过按实际报告区分；MCP `read_workflow_node` 使用 `testCases: true`、可选 cursor 和 limit 分页，默认 50、最多 100。游标绑定原测试尝试和报告摘要，不从当前现场重新采集。测试文件对应使用报告中的文件路径或框架类名；无法明确对应的个案不能被认定为已覆盖。

评审员必须独立完整读取配置、设计、测试报告以及本模块设计范围的全部源码。固定 CODE 文件沿同一个文件 MCP 使用 name、path、sha256、startLine、lineCount 读取，最多 200 行/48000 字符；不能借当前项目或其他模型的阅读记录提交引用。V169 仅为精确只读复核模块追加 SOURCE/CODE 行阅读资格及 JSON 输入阅读资格，原模块保留原范围。阅读账本保持不可改写，停止后的新读取不得入账。

候选逐一包含本模块全部设计场景，提供语义判断、理由、实际测试编号及固定测试文件引用。已覆盖声明必须有匹配测试文件的完整阅读和有效引用，每个场景最多关联 16 个测试、16 条引用。程序决定执行事实：关联失败标为 FAILED，跳过标为 NOT_EXECUTED，旧报告缺少固定输入检查标为 EVIDENCE_INCOMPLETE；缺少测试或断言不足分别保留 MISSING、INSUFFICIENT。只有评审认为全部场景已覆盖、全部关联测试实际通过、固定输入证明完整且原生报告整体通过，最终意见才为 PASS；其他情况均为 REVISE。这是一份带程序证据的独立语义评审，不等同于程序自动证明所有业务行为。

默认完成规则要求 PASS；用户可选择提交有效意见后继续，从而保留返修结果用于后续分支。角色只交候选，最终结果绑定源码、设计、writer、测试尝试和报告摘要；接受意见后仍等待本次模型的独立停止证明。画布分别展示场景状态、原生测试结果和可展开的测试断言，不显示内部身份。此节点不会自动创建额外 Judge；完整多模块/多批次汇总及默认双评审组合继续按显式流程节点实现。

`source.test-review` V2 复核 V2 原生测试中的一批设计，五项输入形式不变。所选设计须属于原测试的固定批次集合；CODE、SOURCE、配置和原生报告仍精确匹配同一执行。每批独立读取、引用和评审，但共享最后一份代码及其实际测试事实；本批测试通过也不能把整体失败的原生报告改成 PASS。V1 复核继续消费 V1 测试，不自动改写冻结协议。V170 只扩展这两个精确 V2 模块的数据库资格；旧命令、交付、报告和阅读账本原字节保留，活动 V1 评审可继续。此能力已接入执行合同，完整分批规划和默认组合仍待接线，预设目录继续保留已有 V1 定义。

## 完整单测分批与汇总

`builtin.workflow.source-unit-test` 从单测用途的冻结源码、测试配置识别开始，经 `system.source.test-plan` V1 产生候选，再进入场景设计、逐批编写、最终代码测试、显式独立复核与结果汇总。新增预设明确选择原生测试和复核 V2；原 V1 预设与已冻结流程不改写。没有新增必经模型规划师。

分批节点复用源码批次规则，先按固定测试模块归属、再按目录和规模划分全部适用目标。每个目标恰好归入一个批次；不明确的模块归属、其他中间结果消费者或不支持的连接形状保持失败。后续初始配置各一份设计、编写、最终测试和汇总，以及与汇总策略一致的零、一、两份复核；双份复核须选择不同角色。角色修订、任务、完成标准、重试、参数和检查点继承到每批。场景设计可并行，writer 显式继承前一批的固定 CODE；各模块均测试最后一批的同一份 CODE，并绑定本模块全部场景设计；每批复核绑定对应模块测试、同一最终代码及本批设计。

候选仍通过原计划确认机制：当前图不会自动替换，连续执行也先暂停等待用户确认。确认后保持暂停，用户明确选择执行范围。候选、派发暂停、交付、停止与节点完成同事务提交；事务失败恢复原尝试，取消后拒绝迟到候选。整体受 256 节点、1024 连接、128 KiB 候选、最多 61 批及 64 个汇总输入约束，完整范围超限时明确失败，不裁剪源码或少生成批次。每个汇总保留 source/profile/code，另绑定各模块测试及每批实际复核；双复核因此通常先受汇总输入上限约束。

`system.source.test-summary` V1 只读本需求固定证据，要求各模块成功收尾的 V2 原生测试和所选 V2 复核均绑定同版 SOURCE、测试配置及最终 CODE。核验原生产者、停止、原输入、交付摘要及实际代码继承链，重复模块测试或重复评审尝试不能增加覆盖。所有固定目标和配置模块均须覆盖。测试报告必须有效、通过且固定输入未变化；场景数量不替代原生测试事实。

汇总的 `reviewPolicy` 为 `NONE`、`SINGLE` 或默认 `DUAL`。NONE 不要求复核，保留实际提供的意见；SINGLE 每批须一份 PASS；DUAL 每批须两份 PASS、不同角色、不同独立 Session 且相同证据基准。用户删除复核节点时同步修改策略，程序不重新生成已取消的复核。来源不合法拒绝执行；范围遗漏、实际测试失败或策略未满足生成未通过报告。默认 VERIFIED 失败会进入原重试/停滞路径；用户也能明确选择保存汇总后继续或指定业务结果，原报告的 FAIL 不被改写。

汇总输出固定 JSON 与文本说明，包含最终代码引用、模块测试、源码范围和逐批复核情况；代码文件继续通过实际 writer 的不可变交付读取。汇总接受、无外部执行停止证明和生命周期同一短事务提交，无进程或模型调用。V171 仅扩展精确无角色规划与汇总模块的停止资格，历史迁移和其他适配器不变。页面展示完整范围、同一最终代码、实际测试和明确复核策略，按需读取正文，不直接显示内部身份。

## 专业源码编写与复核

`source.design`、`source.design-review` V1 为独立只读 WORK 节点，复用现有源码作者/复核员和节点五个私有 MCP。角色新增专业工作说明及适配槽资格，不替换原专业槽位、旧冻结提示或通用流程默认绑定。新节点不创建影子旧 Task，也不通过角色名称取得旧源码工具或额外原生/外部工具权限。

两者须绑定名为 `source` 的成功冻结源码 DOCUMENT。`parameters.targetPaths` 为本批精确路径的 JSON 字符串数组，缺省使用全部可处理目标；不得增加上下文/排除项或重复路径。单批沿用最多 12 个文件、160000 字节的边界，单个大文件独立成批。范围过大在创建尝试前明确阻断，不能截断为部分文件；拆分或修改计划仍需用户确认。

专业角色使用文件 MCP 的行协议，提供输入名称、冻结哈希、起始行及最多 200 行，按 `nextLine` 读取。源码正文在事务外读取并校验；短事务再次核对模型身份、活动状态与停止情况，记录本尝试实际返回的路径、哈希、行区间及正文。原生读取、作者声明和其他尝试的记录不能替代本次阅读证明。V159 以数据库守卫保持读取账本的身份及不可改写边界。

作者交付结构化 JSON 设计及文本摘要。程序复用原专业校验，要求完整读取本批全部源码，章节路径覆盖无遗漏，每份关联源码至少有一条与实际读取内容和行号一致的引用；Markdown 不接受 HTML、图片或自建链接。专业设计/复核正文保留原 256 KiB 额度，仅这两个模块的节点包装额度为 300 KiB；普通交付仍为 128 KiB。字段或引用错误可在原尝试修正，不产生成功结果或新的执行次数。

复核另外绑定名为 `draft` 的本批设计 JSON；其他 JSON 输入表示明确绑定的关联设计稿。设计稿必须来自本需求已成功收尾的专业作者，且与复核使用完全相同的源码生产者和冻结引用，不能混用字节相同但身份不同的采集。复核目标须等于本批设计稿的路径范围。复核员通过输入 MCP 完整读取每份已绑定设计稿，并独立完整读取本批源码，再交付 PASS/REVISE、源码引用及问题建议。程序验证所有绑定稿件的读取区间；不能声称自动核对了未绑定的其他批次。

默认复核完成规则要求 PASS，有效 REVISE 意见保留后按失败/停滞策略处理；用户可改为有效交付即完成，将返修用于条件分支。接受交付仍须等待独立模型停止证明才能释放后继，取消后迟到读取或提交不能复活节点。画布支持本批路径编辑、设计章节、默认折叠的引用及局限、真实返修意见。文档汇总及用户确认的分批组合见下方；大批稿件通过固定输出引用传递，实际 Provider 及旧专业模板全规模资格仍需独立验证。

## 源码分批候选计划

`system.source.design-plan` V1 为无角色的 SYSTEM 节点，消费一份成功的冻结源码，不读取当前目录或调用模型。它复用旧模板的完整划分规则：保持冻结清单顺序，按目录、最多 12 文件与 160000 字节划分，单个大文件独立成批。批次目录和标题沿用清单的 `/` 分隔路径，避免宿主系统改变同一份计划的展示。程序不省略目标，也不把空集合认定为规划完成。

内置“源码详细设计”由源码采集、分批规划、一份作者配置、一份复核配置及文档汇总组成。分批节点以本次冻结计划中的后续节点为配置，继承角色及角色修订、任务、输出、完成规则、重试次数、人工检查点和其他参数，只细化批次范围及连接。每位复核员明确绑定自己的主稿与全部其他批次设计稿；汇总绑定全部设计稿和复核意见。用户删除复核后，须同时将汇总策略设为 NONE；程序不会补回被删除的角色或审查。

细化前要求一份编写配置、可选的一份复核配置和一份汇总配置，按分批→编写→复核（可选）→汇总连接。编写或复核的外部消费者不能被静默丢弃；用户先改为消费汇总成果或手动调整计划。汇总之后的自定义工作及其他无关区域保持原样。生成的方案必须通过完整图校验和来源节点后继范围校验，不能修改来源节点、公共资料或无关依赖。

候选计划、报告、派发暂停、程序停止证明及节点完成同事务保存。失败回滚后仍由原尝试恢复；取消后的迟到计算不能发布候选。V161 仅给这一精确模块增加无外部执行证明资格，模型和命令边界不变。普通候选确认接口处理查看、编辑、退回、版本冲突和确认；确认程序候选以 USER 记录计划修订，保留候选生产者与应用记录，不误标为 AI 生成。确认不附带执行，用户仍需选择执行方式。

当前画布容量为 256 节点、1024 连接、单节点 64 输入；分批带复核最多 31 批、无复核最多 63 批，实际还受完整图及 128 KiB 候选交付限制。超限保留完整源码并失败，明确要求按源码子目录组织流程，不截断为部分计划。多份设计稿通过固定输出引用传递，避免累计正文重复占用输入快照额度；旧入口在等价替代与真实运行资格完成前保留。

## 专业设计文档汇总

`system.source.design-document` V1 是无角色的 SYSTEM 节点。显式绑定一份冻结 `source` DOCUMENT、至少一份专业作者的设计 JSON，以及可选的专业复核 DECISION；实际绑定均为必需输入。所有设计稿须来自本需求已成功收尾的专业作者，并指向同一源码采集身份。复核只授权它实际绑定的主稿，不能用另一稿件的通过意见代替；关联稿的阅读也不等于主稿已通过复核。

`reviewPolicy=REQUIRED` 为默认值，要求每份设计稿都有匹配的 PASS。用户可明确改为 `NONE`，按自定义策略汇总未复核或要求返修的设计；仍保留原意见、真实复核计数及 Markdown 中的未通过说明。选择 NONE 不把失败节点变为成功输入；要消费有效 REVISE，复核节点需由用户明确选择交付即完成。复核策略不放宽源码覆盖、来源、内容安全或文件完整性。

汇总复用旧详细设计的纯渲染器，生成章节文件、`overview.md` 与 `coverage.md`，完整覆盖本次冻结源码的全部可处理目标；遗漏批次或来源不一致产生失败报告，不发布部分文档包。V160 将不可改写清单和 UTF-8 正文保存在 SQLite，最多 1026 个文件、总计 64 MiB。渲染在事务外进行，文件、清单、接受交付、程序停止证明与节点完成同一短事务提交；失败可重试原尝试，取消后不能发布迟到结果。

成功交付 `DESIGN_DOCUMENT` 类型的 DOCUMENT 引用、JSON 报告和文本说明。该引用与冻结源码和 CODE 树分开；HTTP/私有文件 MCP 校验需求、项目、生产尝试、成功/停止事实及清单和正文摘要。文件列表不加载正文，单文件按需读取；明确下载全部文档时读取有界文件集合并在事务外生成 ZIP。ZIP 和单文件使用相同固定字节，不重新读取当前项目或采用最新设计。画布显示完整生成、未完成原因及真实复核情况。

## 节点的项目知识与保存证据

`WORKFLOW_READ_ONLY` 与 `WORKFLOW_WRITE` 允许项目知识能力，实际工具仍取角色能力、适配器、项目工具策略及冻结 Session 许可的交集；不增加实时 SQL、数据库结构、Word 或外部工具授权。知识库助手可作为只读工作节点角色，专业工作说明与知识问答提示分开，节点仍按其任务、交付及完成标准工作。

首次冻结节点角色时同时保存该节点的项目来源集合，后续尝试继承同一集合。已经冻结但没有来源记录的历史节点保持空授权，不因恢复、重试或新增全局能力自动补权限；新 Session 的工具策略可以收窄，已经创建的 Session 保持原权限。知识资料是采集时的补充背景，不替代显式绑定的固定输入。

辅助 MCP 作用域绑定准确的节点尝试、外部 Session、运行代际、目录、角色版本及许可。读取前后均复核当前尝试；保存成功回执前在同一短事务复核活动状态并更新原调用，取消后不能接受迟到的成功证据。资料读取在事务外。停止、终态、失效身份、其他节点私有引用及越界路径均拒绝；结果中的临时工具凭证被移除，交付中携带此类凭证会被拒绝。

画布“检索证据”按所选历史尝试分页读取成功调用的元数据，点击后才读取保存正文，来源文件后续变化不改写原记录。查询同时校验需求、节点、尝试、Session 和调用所属身份；允许用户查看已结束尝试的历史，不重新授权模型继续工作。读取历史引用的工具调用不再重复列成新的原始证据。正文最大 1 MiB，前端最多缓存三份；分页、正文失败与切换尝试各自保持恢复边界。

### 知识证据交付给后继

`knowledge.research` V1 使用只读模型适配器，必需交付 TEXT `result` 和 JSON `evidence`。模型仅提交 `{version:1,references:["call:…"],limitations:[…]}`，最多 12 份本 Session 成功的原始知识调用；不得传入自行拼装的来源正文或摘要。程序按尝试、Session、调用拥有者核验，并从已保存回执编译 `KNOWLEDGE_EVIDENCE`：实际工具、调用时间、固定正文、正文 SHA-256 及局限。读取历史引用的调用不作为新的原始记录，其他节点私有引用、伪造或重复引用拒绝。

搜索、目录及未完成分页保留原工具和覆盖提示，仅作为线索，不能冒充完整原文。可以交付空证据集合，但必须说明未查到或无法读取的具体缺口；不能由无命中推断全项目不存在资料。普通节点 128 KiB 完整交付上限不变，原回执或所选集合超限时整体拒绝，要求缩小实际读取范围，不静默截断引用。

选中的正文与节点交付、幂等回执在同一事务接受，异常整体回滚并可用原请求重试。节点独立成功收尾后，后继按已有固定输入引用取得该 JSON 交付；来源后来改变不重读，未选择的私有调用不传递。后继可用原工作 MCP 按页读取完整正文，不需要也不获得生产者的辅助 MCP 作用域。画布同时为本节点交付和后继固定输入提供资料选择、原文及局限展示。

内置“知识检索与资料整理”组合先查询并选择固定证据，再由资料整理节点读取结论和证据形成说明；用户可修改角色、任务及后续工作，或自行增加人工检查。节点没有附加新的审查、测试或规划师。

## 规划能力与动态修改

流程规划能力把目标/设计成果组织为具体工作、依赖和输入输出关系，由适用的现有角色承担。
不强制新增流程规划师角色，也不在默认流程中强制增加独立规划节点。
设计节点可以同时交付设计方案和候选计划；已有结构化阶段安排由程序确定性转换，避免重复模型调用。
复杂任务需要单独规划时可选择“生成候选流程计划”工作模块，绑定现有任务规划师或用户配置角色。
界面称“候选计划”或“计划变更”，标出实际来源节点，不用虚构角色作为默认作者。
模型生成的变更是候选计划；单步与连续执行均必须先展示给用户，确认后生效。
候选展示新增、修改、移除及影响消费者，绑定基准计划版本与允许修改区域。
用户可直接接受、编辑后接受或退回重新规划。手动编辑点击应用即为明确确认，不重复弹出同义审批。
确认原子复核当前计划和节点状态；过期候选不能覆盖已经执行或已经调整的计划。
存在待确认候选时暂停新节点派发，已经启动的节点按原计划收尾；停止当前节点是独立动作。
只读自由工作节点可通过声明一个 `PLAN` 输出提交 `{version:1,baseRevision,graph}`。来源尝试固定基准计划及允许改动的后继区域；来源节点、其他区域和公共资料声明原样保留。当前文件工作节点不承接规划输出。
声明 PLAN 的活动节点可通过原工作查询 MCP 分页读取预设摘要，再按明确预设版本取得节点内容和真实角色修订。模型据此提出后继节点，不猜测角色标识。查询不创建运行或扩大当前角色权限；其他节点、已停止或身份失效的尝试不能调用这项规划查询。
候选接受、交付物和 MCP 回执同事务持久化，来源节点成功收尾后才可应用。候选详情包含原计划和候选，按需读取；列表只读摘要并分页。应用保留原候选，用户编辑后的版本写入新的不可变计划修订。退回不改写来源交付物，也不自动重跑模型；可自行调整后续工作。

未开始节点可以修改；正在运行节点先停止并取得证明才能改其执行内容。
失败节点原样重试产生新尝试；修改任务再执行产生新节点定义版本及新尝试。
完成节点的历史不改写；重做明确建立新一轮。删除表示移出当前有效计划，不物理抹除历史成果。
仍有输入消费者的删除/替换必须提供新输入或取消消费者；缺失输入禁止执行。
应用运行中调整时，未变节点继续引用原运行身份；受影响且可修改的后续节点建立新的定义，历史尝试及累计序号保留。仍然保留的已完成或活动节点及其前置依赖不能被改写。公共资料声明与已经固定的内容继续冻结；新资料通过明确的后续交付物传递。
待检查节点必须先确认检查点，不能用删除跳过检查。原单步或运行至节点目标被移除时，旧执行范围仅保留为暂停的历史引用，不扩大为连续执行；用户重新选择执行范围。应用计划后暂停派发，不自动开始新工作。

## 执行控制与完成

支持执行此节点、执行到此处、连续执行、执行后暂停、暂停后续派发及停止当前节点。
单步不能绕过前置条件；运行至节点只调度其必要依赖闭包，不能误跑无关分支。
人工检查点是真实持久化等待条件；刷新、重连、重新打开页面不自动确认。
执行画布使用同一只读事务返回控制与节点摘要；执行历史按需分页，输入、交付物与模型活动按尝试展开读取。历史详情采用该尝试的冻结节点定义与角色版本，不用当前模板替换。模型活动读取在事务外进行，内容有界并隐藏作用域凭证；连接失败只影响日志投影，不能改变节点状态。
页面写操作保留原请求与回执：未知结果重试原命令，已经接受而刷新失败只重读；切换节点或需求后迟到的读取结果不得覆盖当前详情。未保存计划及未提交的人工结果离开前提示，刷新检查点仍须明确勾选确认。
执行控制独立保存模式、目标、计划版本、模型选择和控制版本。暂停阻止新尝试准入，已准入的节点按原尝试收尾；停止当前节点是另一个动作。节点准入在目录预检之后的短事务内再次校验控制版本，已经确认的暂停不能被旧调度快照绕过。
工作节点和程序节点的执行后暂停记录绑定成功尝试，并与交付接受、节点终态和资源收尾原子提交。恢复执行须明确确认当前全部待处理检查点；并行节点后来完成产生的新检查点使旧确认失效。末节点的检查点未确认时需求仍不完成。人工节点的完成操作本身就是人工确认，不再重复生成同义检查点。
技术失败按配置次数重试，停止未知不得新开重叠运行；耗尽后停滞且停止新节点派发。
配置重试次数表示首次尝试之外允许的自动重试次数，切换执行方式不重置累计次数。耗尽后对失败节点明确选择单步重试，仅授权下一个尝试序号；不会重新补满自动重试额度。需要恢复原 Session 或证明停止时必须先处理原尝试。
业务结论需要修复是有效结果，可选条件分支；模型断线和无有效结果不是该业务结论。
计划修订、用户重试不能偷偷重置任务累计预算或抹除失败证据。

完成由用户配置的流程及节点规则决定，允许无审查流程；不存在后台隐藏的强制业务审查。
默认开发流程保留默认验收节点，复制后的自定义流程可删改它们。
当前选中执行路径全部满足完成规则、无未处理失败、运行与资源状态完成收束后任务完成。
可选择提交有效交付物即完成、指定程序验证通过、选定评审结论或人工确认等节点完成规则。
前端展示实际采用的完成依据，不把“流程完成”扩大为从未执行的测试或审查已经通过。
人工提前成功、失败和取消保持来源与原因；原验证与审查结论不改写，先收束活动工作。
提前结束通过带本地页面标识、请求键和需求版本的独立命令发起，保存不可改写的用户决定及其原因。需求先进入 STOPPING，控制器停止新节点派发；各适配器使用原尝试、原命令或原会话取得停止证明。后台恢复从持久化意图继续，不重新创建执行身份。
确认所有历史尝试已终止且有停止证明、模型与命令已结束、写入队列和工作区已收束、该需求不再持有目录租约后，才按用户决定原子记录 COMPLETED、FAILED 或 CANCELLED 与结束时间。停止未知、目录恢复失败或最终事务失败均保留意图和原证据，不提前显示成功，也不释放仍有风险的租约。
画布区分“正在结束需求”和“人工认定成功／失败／用户取消”，展示原因。未知写入回执重试原请求，已接受后读取失败只刷新；节点停止未知时可查看原执行记录并重新检查停止。人工结果不将原节点改成成功，也不把待检查点、失败报告或未执行节点改成已通过。规划前取消的历史入口保持原合同。
成果提交是独立动作，连续执行/任务成功不自动授权推送、发布或外部部署。

节点的固定 CODE 输入和已接受输出可按需查看改动文件。列表来自不可变清单，按路径稳定分页并绑定该份交付与清单类型；展示相对原始基线的累计新增、修改、删除，包括继承的上游代码。删除路径即使不在结果文件树中仍保留记录；仅权限变化也属于修改。读取不扫描当前目录，不把新暂存文件加入旧交付。文件列表游标与改动列表游标不可混用。

失败且已经停止的节点可查看自身已接受 CODE 的改动和文件；这种查看资格不允许把失败成果作为后继输入，也不产生任务成功或成果提交事实。页面只在主动展开时分页读取，错误保留已有记录并从原游标重试；切换尝试后不接受迟到的旧结果。


### 需求代码成果选择与只读预览

需求画布提供按需展开的代码成果列表，按需求当前计划及节点最新尝试筛选已停止、已接受 CODE 的成功/失败结果。列表仅返回节点/交付名称、尝试顺序、真实状态、时间和文件计数，不返回交付正文或文件字节。采用时间加来源身份稳定分页，默认 50、最大 100；游标绑定需求及计划修订，不能跨需求或在计划修改后复用。移出计划的节点不再列入当前成果，原历史查看入口继续保留。

用户必须明确选择一份代码成果。预览重新核验计划修订、节点/尝试/命名输出、交付摘要及固定代码清单，展示 Git/普通目录类型、记录的来源分支，以及相对原始基线的累计新增/修改/删除和完整文件规模。包含继承的上游代码，不自动合并并发分支的多个结果。后续确认可据需求版本、来源与预览摘要检测变化，不能把列表摘要当作提交授权。

列表及预览只读 SQLite，不调用模型、Git、当前目录或租约动作；原项目离线以及用户后来修改暂存区/文件不会改变预览。查看改动或下载仍按原节点固定 CODE 的命名绑定读取。失败成果保留失败状态，查看不授予后继输入或成果发布资格。文件可用性和实际提交仍由后续独立提交动作验证，预览不宣称已提交、推送或回填。

页面首次展开才读取列表，选择后才核对该版本，改动清单继续按需读取。分页失败保留已读条目并从原游标重试；切换来源、计划版本、需求或关闭面板后，旧响应不能替换当前内容。预览与下述明确提交确认保持独立。


### 确认固定代码的本地提交

已完成或人工认定成功的需求，且全部历史尝试、模型、命令、写入队列、工作区及租约已经收束后，用户可将一份明确选择的 Git 代码成果保存为本地提交。确认携带需求版本、计划修订、节点/尝试/命名输出、预览摘要、单行提交说明及请求键；后端重新核验全部来源，不从当前暂存区或文件重建交付。人工成功可明确选用已保存的失败节点成果，保留原失败结果；失败或取消的需求尚不提供本地提交入口。

一次确认冻结不可变提交意图：原项目及仓库身份、完整基线与结果树、原始父提交、成果引用、提交说明、时间及作者 `Loopper <loopper@localhost>`。每个需求保留一份确认记录及独立 `WORKFLOW_PUBLICATION` 状态，当前动作新建 `loopper/results/…` 成果分支。同请求同内容返回原记录，改内容、换需求或再次选择其他成果均不能覆盖原确认。确认短事务不执行 Git；V186 持有不可改写意图，V187 补充 SQLite 空值语义下的成功回执守卫，已执行迁移保持不变。

后台以有界并发从已确认记录恢复，在事务外重新检查原目录身份、完整 Git 树、项目范围、受管代码字节及父提交。只从冻结树和提交元数据生成确定性对象，再通过 create-only 引用操作建立成果分支。不会切换 checkout、暂存当前修改、移动来源分支或覆盖已有不同引用；不申请工作目录 writer 租约，因为该动作不操作工作区。来源分支后来前进或用户留下暂存/未提交文件，均不混入本次结果。

Git 返回未知、回执写入失败或目录/对象不可用时进入可恢复阻断，原身份和证据保留。审计与界面分别说明目录、成果数据、提交对象、成果分支或数据库回执的待核对原因；只保存受控原因码，不保存原始进程输出。用户恢复原提交后，继续使用同一树、父提交、作者、时间及分支。已经创建相同引用可核对后补记成功，不同或符号引用保持阻断；迟到失败不能覆盖已确认成功。重启只处理已有确认，不自行生成新的确认。

界面按需读取提交记录，明确确认后才写入。网络回执未知时保留原请求；已接受后读取失败只刷新。关闭/重开或刷新画布后仍显示所选成果、真实节点结果、分支、提交与状态。这里的“已保存本地提交”只证明本地 Git 对象与成果分支；远端推送使用下述独立确认；普通目录回填和外部部署仍是后续独立动作。


### 确认成果分支的远端推送

已保存本地提交后，用户可以选择原项目的一个 Git 远端，主动检查其唯一推送地址和成果分支，再明确确认。打开画布和读取推送状态只读元数据，不联网、不推送；远端名称读取只检查本地配置。检查目标及确认均要求本地 UI 标识；预览绑定本地提交版本、仓库/项目/Git 目录身份、准确地址、分支、固定提交/树及已观察的远端引用。确认前重新检查；远端、地址或引用变化使旧预览失效。每个需求保留一份不可改写的远端确认，后续恢复继续使用原目标。

`WORKFLOW_PUSH` 独立保存 PREPARING、RUNNING、BLOCKED、PUSHED，不修改需求、节点或本地提交状态。V188 保存确认、尝试、监督进程和回执的身份及版本；V189 修正成功标记末尾换行的 SQLite 校验，保留原迁移。确认短事务只写元数据；Git、网络、凭据环境和子进程均在事务外。后台只恢复已确认的记录，检查失败进入阻断，由用户明确恢复。

推送只针对冻结提交和 `loopper/results/…` 分支。先读取准确远端引用：相同提交可直接核对登记；不同提交保持阻断。不存在时以空期望引用的原子 create-only CAS 创建，远端在检查后被并发创建也不能覆盖。Git 的 `--force-with-lease=<ref>:` 在这里仅表达该引用必须不存在，不授予替换历史的权限；不使用 `--force` 或 `+` refspec。禁用自动标签、子模块推送和 HTTP 重定向，不修改当前文件、index、来源分支或 upstream。命令回执无论成功与否都重新核对远端；只有准确分支指向冻结提交且监督进程停止已证明，才能记为 PUSHED。

每次实际执行先准备不可变命令，再注册精确 PID/启动时间并保存，之后才发放执行许可。回执写入失败继续读取原监督进程结果；停止未知只恢复原尝试，不创建第二个 worker。已持久化失败的尝试，必须再次取得同一结果及停止证明，才可在用户明确恢复后创建新尝试。新尝试先核对原远端引用，之前已经完成的推送不会再发一次。进程退出、Git 返回码、数据库成功和远端引用事实分别校验。

HTTP(S) 使用项目覆盖或全局继承的 Git 账号，通过受监督子进程的临时环境传递并按 origin 限制；SSH 使用系统配置。URL 不允许携带 HTTP 凭据、查询参数等敏感内容，多个推送地址必须先整理为单一目标。凭据不进入意图、命令、回执或仓库配置；worker 只输出受控状态码，不保存原始 Git 诊断。运行前重新核对项目身份、本地成果分支和原远端配置，改变目标不会被静默接受。

界面展示“已保存本地提交”与“已确认推送”两个事实。未知确认回执保留请求键及原正文；确认已接受但重读失败只刷新结果。选择目标或回执未确认时保护其他画布写操作，并在离开时提示。刷新或重新进入仍展示持久化状态、原目标和恢复入口；成功记录证明当时已核对的结果，不宣称远端以后永不改变。



### 普通目录成果的回填前检查

需求画布选择一份普通目录的固定 CODE 后，可主动检查原目录。仅已完成或人工成功且全部执行/租约已收束的需求可检查；所选成果可以保留原节点失败事实，不改变该节点状态。检查命令带本地 UI 标识、需求/计划修订、节点/尝试/命名输出及来源预览摘要；源记录在同一个短只读事务内核验，现场 Git/文件读取在事务外进行，完成后再次核对来源。

检查使用三份明确清单：原始基线、所选成果和现在的目录。只应用成果相对基线的改动；成果未修改路径上的用户新增、修改、删除均保留。目标路径现在仍为原版本或已经等于成果版本时可形成预览；第三种内容、执行权限冲突、原文件意外缺失、目录/文件形状碰撞均列为冲突，不能生成目标清单。忽略规则不能隐藏已命名目标；替换目录前额外检查未纳入清单的忽略/受保护子项，保留它们且在任何其他文件修改前阻断。

预览返回当前及目标清单摘要、预计新增/修改/删除数、保留后续修改数、冲突总数及前 100 个相对路径；不返回文件正文。摘要绑定需求、固定成果、当前目录内容及冲突集合。更换来源或目录内容后旧摘要不能代表新结果；浏览器切换选择、关闭或离开后丢弃迟到响应。刷新画布不会自动检查现场。

这一步没有写入授权，不申请租约，不改文件或保存成功事实。`WorkflowDirectoryChanges` 形成确定性差量；`WorkflowDirectoryTransform` 执行一个已固定前后版本的可恢复文件转换，现有节点 SEED/RESTORE 已改用该算法，节点专用账本仍由 `WorkflowDirectoryMutations` 持有。实际写入遵循下述独立确认与恢复合同，不能把“检查通过”标为“已回填”。


### 确认普通目录成果回填

用户查看无冲突的目录检查后，单独确认本次新增、修改、删除、保留修改数及原目录。确认带本地 UI 标识、幂等请求键、需求版本、所选来源和检查摘要；服务端重新检查现场，旧摘要不匹配时不保存意图或申请租约。同一请求键只重放同一请求，确认回执未知也不能换键重发。当前仅完成或人工成功的需求具备回填资格；失败、取消需求的扩大资格未启用。

V190 保存独立 `workflow_writeback`、不可变前后清单、原始固定 CODE 来源及用户检查摘要，不借用已终止节点的执行身份。回填队列与旧 Task、流程写入节点共用 canonical 目录、指纹、全局 FIFO 顺序及唯一 `workspace_lease`，三种持有人互斥。所有排队位置、祖先/子目录冲突、旧任务手动协调与自动释放均识别回填持有人；不能强制收回其写入权。排队不会重新选择来源或采集新的覆盖基线。

获得写入权后，目录必须仍与用户确认的当前清单一致，且不存在本操作未开始时出现的临时文件。程序先保存整份当前文件及目标字节到独立的不可变内容目录，复核清单后才记录 `APPLYING`。尚未准备完成时文件备份可按同一摘要续传；已进入应用阶段后，只能读取原备份与目标对象，缺失或损坏不能从部分现场重建。任何文件、Git 和进程 I/O 都在 SQLite 事务外。

同一回填操作的所有恢复执行共用受管目录内的 OS 文件锁，持有期间只由当前线程调用共用 `WorkflowDirectoryTransform`。另一个 JVM 持锁时不启动写入；进程退出释放锁后，恢复仍须复核原记录及共享租约。每个实际文件只接受固定前值、后值或属于本次已开始应用的有效临时前缀；第三种内容、链接、目录身份变化、忽略/受保护子项及备份损坏保持阻断和原租约。阻断后由用户显式恢复同一操作。

全部写入结束并再次核对目标目录后，程序仍持操作锁，在一个短事务中保存目标摘要/租约版本回执、推进 `APPLIED`、结束回填队列并交给最早等待者。该事务回滚时文件可以已经是完整结果，但状态及写入权保留；恢复只复核并补同一回执，不再次覆盖文件。事务已经成功后的重复推进或重复确认只读取记录，不触碰下一位持有人的目录。

画布读取持久化回填状态，无须重新选择成果即可看到排队、应用中、阻断和完成记录。确认面板与未知回执期间保护其他画布写操作；确认已接受而读取失败只刷新结果。已确认记录出现后收起旧的回填前检查，避免与完成状态混淆。完成记录证明当时已核对并保存原文件备份，不宣称目录之后不会被用户或其他任务修改。


## 普通目录写入与恢复

非 Git 项目的基线保存使用受管私有对象库，用户项目不初始化 `.git`，执行目录及写入租约仍指向原目录。V162 的准备记录先固定尝试、需求、项目、输入摘要、原目录身份和私有存储位置；只有持有有效写入租约的 PREPARING 尝试可以创建或补齐，排队、停止未知或已经停止的尝试不能获得准备成功事实。

采集两次比较普通文件清单，固定原字节、可执行权限和摘要后，先保存不可改写清单，再复制文件。单文件 4000000 字节、最多 10000 文件、总计 128 MiB，准备清单最多 16 MiB；超限明确失败。忽略文件、敏感文件及 Loopper 受管数据不进入交付；后续采集仍显式跟踪已有清单的文件，不因新增忽略规则丢失原文件。符号链接、目录替换和新的 Git 归属均不能悄悄改变原身份。

复制中断后复用原清单，已经保存的正文按摘要读取；尚缺正文必须与原清单一致，不能重新采集当前项目替换旧基线。损坏对象不能当作缺失对象覆盖修复。私有 Git 对象直接使用固定原字节，不运行内容过滤器，不改项目索引；同一清单及准备身份重试生成相同树和基线提交。文件和 Git I/O 在事务外，保存清单及准备成功时重新校验尝试、项目版本和租约。

准备记录只证明基线已经保存，不授予模型启动、覆盖当前目录或接受 CODE 交付的资格。`WorkflowWorkspaces` 根据原项目归属选择 Git 或普通目录适配，已经准备的尝试始终使用原适配；目录中后来新增 Git 归属会阻断恢复，不能切换合同。两种适配复用正式 Start、模型身份、候选接受、独立停止证明、工作区生命周期和原子租约交接。

V163 区分原执行目录与受管对象库。工作区和 CODE 的 `object_repository` 为可空字段，历史 Git 记录保持空值及原语义。普通目录模型仍在原项目执行；子节点的工作区 CODE 输入必须来自本需求的成功节点，且原始基线树一致。先固定 SEED 应用记录的前后清单，再从已授权的固定交付复制字节并回填；准备完成及模型创建前再次核对实际文件，用户后来改变基线时保持阻断。

确认模型停止后，先保存不可改写的结果清单，再复制固定正文、生成私有检查点及 CODE 引用。结果清单已保存时不能重新采集新文件替换旧结果。恢复前保存 RESTORE 应用记录；每个现存文件须对应这次操作的前版本或后版本，未知文件及内容变化阻断恢复。临时文件只认不可变应用身份派生的精确名称，恢复只接受固定目标字节的前缀并完成原写入；不扫描删除其他临时文件。

文件与目录之间转换只删除已记录的原文件和必要的空目录，受保护或忽略文件不会为了完成恢复而被删除。符号链接、损坏对象、后续用户修改和停止未知均保留现场与原租约。尚未产生工作区变更的准备取消仅收束原记录；已发生回填或执行的取消保存和还原原工作，不能通过取消覆盖用户后来的修改。租约释放及交付接受仍在同一最终事务；已交接回执重放不触碰新持有人的目录。

## 固定交付物的程序检查

`system.verify.files` V1 是无角色的 SYSTEM 节点，必须绑定一份必需的上游 CODE 输入，按冻结清单读取文件；不读取当前工作目录、不启动模型、进程或网络。参数声明 1–16 项文件内容、SHA-256 或文件移除检查；内容支持完全一致或包含，保留期望文本的空白。文件移除只证明该固定交付版本中不存在对应文件或目录内容，不证明运行环境或忽略文件已经被删除。
程序生成文本说明和 JSON 报告，保存每项检查结果及固定输入血缘；角色不能代交这份程序报告。完成条件为“全部检查通过”时，未通过按原重试规则处理，耗尽停滞；用户也可明确选择完成检查即继续，将有效的未通过结果用于修复分支。固定文件缺失、损坏或无法按要求读取属于检查错误，不能作为有效业务结果继续。
保存报告、无外部工作证明、节点终态及检查点在一个短事务中提交，读取文件在事务外。重启或保存结果失败可以对同一尝试和输入重算，不新建模型或申请写目录租约。此适配器的无外部工作证明不能用于任何模型或命令执行模块。
画布提供检查项配置及逐项报告；失败尝试的报告仍可查看。此模块不提供测试命令、浏览器、HTTP 或语义评审，文件检查通过不能扩大为这些验证已经完成；其余验证需要专门执行适配及恢复证明。

## 固定交付物的命令检查

`system.verify.command` V1 已接入命令检查预设、画布配置、诊断与执行记录。它使用一份必需 CODE 输入，复制固定字节和可执行权限到本尝试的独立检查目录，不修改项目 checkout 或不可变输入。只有准备阶段可以核对并继续未完成的复制；开始执行之后不重建或重置该目录。
参数为独立 argv、1–3600 秒时限、测试或普通检查用途及可选输出片段。拒绝 Shell 启动器和片段；TEST 使用已有框架策略拒绝未知或跳过测试的命令，Maven 规范化及平台可执行程序解析后再次校验。Gradle 须使用 `--no-daemon`。该合同不把普通检查、文本搜索或零退出码扩大为未声明业务标准的测试覆盖，也不提供浏览器或 HTTP 断言。

候选提交、计划诊断和应用共享运行准入的命令定义解析。已经配置的命令须符合所选用途，普通检查脚本应使用 CHECK；不允许先接受错误用途、到检查节点才暴露错误。尚未确定的空 argv 可作为规划占位保留，但该节点正式执行时仍严格拒绝。模型提交错误候选时不接受部分交付或创建候选记录，可在原尝试内修正；草稿保存与执行资格仍分开。

节点、尝试及 `WORKFLOW_COMMAND` 命令状态分开。程序先持久化本次意图，在事务外复制文件、准备不可变请求，再登记独立监督进程的 PID 与启动时刻。SQLite 保存并确认该身份后才发布执行许可。重复启动监督程序通过文件锁和不可变登记保证原命令只启动一次；服务重启读取原请求、进程身份和结果，不能按新身份重发。
监督进程保存有界输出和退出状态；正常结束、超时、输出超限及取消都核对已观察的进程树停止情况。使用 JDK 的进程身份与树观察，不是操作系统沙箱，不能声称隔离任意脱离监督的恶意后台进程。监督进程异常消失且没有最终回执时保持停止未知；恢复只重新核对原身份，不能通过重试消除不确定性或伪造停止证明。

底层命令协议 V2 可在同一不可变请求内携带最多四个准备步骤，每步固定 argv 与位于本次私有目录内的工作目录。登记和执行许可覆盖整个请求；准备依次执行，只有上一进程正常成功且确认停止后才能进入下一步和主检查命令。所有步骤共用请求总时限，保存的 UTF-8 输出合计最多 64 KiB；异常编码替换导致文本膨胀时按完整字符截断并标为不完整。取消作用于当前进程树。准备的进程身份及结果分别保存，最终回执同时携带准备与主命令结果；准备失败、超时、取消或输出不完整时主检查不启动，也不能成为允许继续的有效 FAIL。缺少最终回执仍保持停止未知，不从部分准备记录推导可重跑。
无准备步骤继续使用原 V1 二进制和规范化 JSON，不新增空字段改变历史摘要；V1/V2 均按原冻结请求恢复。界面从按需读取的执行证据区分准备步骤与主命令，并明确显示未执行的后续步骤。原生单测适配器已将 npm/Python 环境准备接入这一请求；普通命令仍按用户声明的单命令执行，不隐式安装依赖。原生环境的具体声明、固定输入检查和已验证平台见前文。

完整正常执行的非零退出或输出不匹配可以作为有效 FAIL；是否继续由节点完成规则决定。启动错误、超时、输出不完整与取消不构成可继续的业务结果。原始结果在命令账本保存，节点报告提供有界摘要；输出截取须明确标记。报告、匹配原请求的命令停止证明、节点终态、命令终态及执行控制结算原子保存，数据库收尾失败可恢复同一回执，不再次运行命令。
用户停止及恢复使用本地 UI 授权、原尝试作用域、版本和幂等键；原始证据按需读取。停止前尚未冻结请求时，只有同事务确认该尝试不可能再获得启动许可才能生成未启动证明；已冻结请求使用监督程序的实际最终回执。命令停止证明不能借用纯文件的无外部工作例外，也不能用于模型 Session。
画布将程序和每项参数分别编辑，不擅自拆分 Shell 文本或裁剪参数/输出片段的空白；预设不猜测项目的测试命令。节点摘要仅返回命令状态、版本与恢复原因，不读取执行正文。报告区区分有效的检查未通过和执行不完整；执行记录按需读取冻结请求、监督身份及结果，服务端先核对请求和结果摘要。停止或恢复绑定命令自身的版本，回执未知时重放原请求；迟到的读取不能覆盖其他尝试或较新的记录。

## 默认开发流程与独立评审

默认组合为：需求提问 → 用户补充与确认 → 设计与候选阶段计划 → 文件开发 → 程序验证 → 并行的需求/风险评审 → 同批验收。新建需求默认读取服务端发布的开发流程修订；从流程库指定的其他流程优先。内置组合支持覆盖预设的节点名称和任务说明，实例仍保存完整配置，不在执行时读取可变预设。
设计师从真实项目确定检查命令并写入候选计划，用户确认后才应用。初始命令为空，不假设所有项目都用同一个框架；没有合法命令时该检查节点不能启动，但不阻止先执行需求和设计节点。计划确认的结构检查不等于每个模块已具备运行资格。可选需求原文通过固定公共资料交给提问与设计节点，由文件 MCP 读取清单、正文及解析局限。文件工作支持 Git 与普通目录，最终提交或回填是独立确认动作。

`review.requirement` 与 `review.risk` V1 复用独立只读模型会话及原五个节点 MCP，分别默认选择已有需求评审员和风险评审员。每个节点必须固定设计 TEXT、代码 CODE、程序验证报告 JSON 三项上游输入；报告包含 PASS/BLOCKED、理由及已读取的证据名称。PASS 须引用三项；BLOCKED 是有效意见，不诱导模型为了完成节点而改为通过。专业角色可由用户配置，实际权限仍由只读适配器限制。
模型只提交意见。程序校验格式并将原需求、目标、全部精确输入身份和内容的规范摘要写入报告；模型不能提供或覆盖批次摘要、来源身份和程序验收事实。可修正格式错误沿用同一尝试与会话，不消耗新执行次数。接受意见后仍等待该模型的独立停止证明；其他评审不会消费尚未收尾的意见。

`system.review.dual` V1 是无角色的程序汇总节点，显式绑定两份 DECISION。它核对两份报告分别来自需求与风险模块的不同成功尝试、属于本需求、具有停止证明和同一批输入，并追溯程序报告对应的实际 CODE 版本。仅把待评代码添加成验证节点的另一个未使用输入不能充当已验证。两位 PASS 且该批程序验证通过才产生验收 PASS；来源或批次不一致则阻断，不合并不同版本的通过意见。
验收汇总只读取持久化证据，不创建旧 Task、隐藏 Judge、外部进程或模型；准入、结果、无外部工作证明、终态、检查点、控制结算及幂等回执在同一短事务提交。回执保存失败整体回滚，原命令可以重放。V156 只为这个精确程序适配器追加无外部工作证明例外，保留原模型、命令和纯文件检查守卫。
用户可删改自定义流程中的评审和验收，或明确选择将有效未通过结果用于条件分支。移除这些模块后不暗中恢复自动验收；报告仍保留原程序验证和意见。界面分别展示两位评审的真实结论与原因、程序验证结果和汇总结论，不把流程完成扩大为未配置的测试、审查或发布已经完成。

## 入口与兼容

流程库、需求列表、新建需求与画布共用三套应用皮肤；颜色、字体、圆角、阴影和按钮状态由皮肤配置持有，不将画布固定为某种配色。
流程创作与需求规划／执行默认以宽阔画布为主体，添加、公共资料、流程设置与辅助工具按需展开。选中节点或连接才展示对应详情；切换选择更新上下文，重复点击同一对象不重置正在填写的内容。空白点击、关闭按钮和 Escape 取消选择；平移画布不误取消选择。
节点列表通过辅助工具打开，可搜索并定位视窗外节点。缩放、适应画布、节点与连接的键盘操作保持可用。只有选择节点后才展示该节点的连接或执行操作；执行范围、状态与写操作授权仍遵守本合同。
收起界面不等于放弃业务操作：人工填写内容沿既有离开确认保护，上传中、未知写入回执、检查点、待决策候选、停止与可恢复错误保持可见且可恢复；不会通过卸载面板丢弃待确认命令。

新增流程库，需求任务承接设计工作台，任务详情以共享画布为主体。
取消新建大型任务和需求开发模板的重复入口，复杂目标通过子流程/动态计划表达。
主页、任务列表和历史设计列表的新建按钮统一进入 `/requirements/new`，项目入口保留指定项目。旧 `/designer` 新建地址转入该入口，并保留可导入的未发送文字；明确的 `sessionId` 或旧工作区已保存会话仍打开历史设计。历史会话重新开始时，先按原协议停止及归档，再进入新需求入口。模板任务目录不再展示 `REQUIREMENT_DEVELOPMENT` 新建表单，原上传记录和历史详情继续可达；恢复服务及冻结协议保持。
其他模板逐一转换为可配置内置流程，其来源参数、专用交付物与完成合同不能丢失。
历史设计、任务、模板、恢复与已存在审批继续按冻结版本处理，不套用新自由完成策略。
阶段二的模块化先保持旧行为，新规则只在正式接线的新流程代际中生效。

## 必需验收场景

- 模板复制、编辑和实例隔离；预设与自由节点共同执行。
- 两父节点输入、条件未选分支、并行汇合、缺失输入、环与悬空连接。
- 交付物重复提交、异内容冲突、越权读取、旧版本与迟到结果。
- 候选必须确认、候选过期、确认时节点已启动、人工编辑后应用。
- 失败耗尽、停止未知、重启恢复、替换失败节点、上游重做后的消费者提示。
- 删除审查后的新流程无隐藏审查；默认流程保留默认验收；历史任务仍按旧规则。
- 同目录并发 writer 被串行化，读取和只读节点能按授权并发。
- 单步/运行至节点/连续/断点行为不同，刷新不改变控制状态。
- 提前结束先收束执行，提交与完成保持独立。
